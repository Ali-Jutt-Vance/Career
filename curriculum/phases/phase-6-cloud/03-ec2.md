## Beginner Theory

### Instance Types

```
Instance Family Naming:  [family][generation][attributes].[size]
                         t3.micro   c6i.2xlarge   r7g.4xlarge

Families:
  t (burstable):       t3.micro, t3.small — baseline CPU + burst credits
                       Best for: dev, test, low-traffic apps
  m (general purpose): m6i.large — balanced CPU/memory
                       Best for: web servers, databases, app servers
  c (compute):         c6i.2xlarge — high CPU ratio
                       Best for: batch processing, ML inference, media encoding
  r (memory):          r7g.2xlarge — high memory ratio
                       Best for: in-memory databases, Redis, SAP HANA
  i (storage):         i3.xlarge — NVMe instance storage
                       Best for: high IOPS databases, Cassandra, Elasticsearch
  g/p (GPU):           g4dn.xlarge, p3.2xlarge — GPU instances
                       Best for: ML training, video transcoding, graphics

Sizes:          nano < micro < small < medium < large < xlarge < 2xlarge ...
Generation:     Higher number = newer hardware, better price/perf ratio
Processors:     a (AMD EPYC), g (AWS Graviton ARM — 20% cheaper), no suffix (Intel)

Graviton (g) instances:
  ARM-based, AWS-designed — up to 40% better price/performance
  t4g, m7g, c7g, r7g — use for any workload with arm64 support
  Docker images must be built for linux/arm64
```

## Basic Examples

### Launch EC2 with Terraform

```hcl
# Data: find latest Amazon Linux 2023 AMI
data "aws_ami" "amazon_linux_2023" {
  most_recent = true
  owners      = ["amazon"]

  filter {
    name   = "name"
    values = ["al2023-ami-*-x86_64"]
  }

  filter {
    name   = "state"
    values = ["available"]
  }
}

# Security Group
resource "aws_security_group" "app" {
  name        = "myapp-sg"
  description = "Allow HTTP, HTTPS from ALB; SSH from VPN"
  vpc_id      = aws_vpc.main.id

  ingress {
    from_port       = 80
    to_port         = 80
    protocol        = "tcp"
    security_groups = [aws_security_group.alb.id]  # only from ALB
  }

  ingress {
    from_port   = 22
    to_port     = 22
    protocol    = "tcp"
    cidr_blocks = ["10.0.0.0/8"]  # only from VPN/internal
  }

  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"   # all
    cidr_blocks = ["0.0.0.0/0"]
  }

  tags = { Name = "myapp-sg" }
}

# EC2 Instance
resource "aws_instance" "app" {
  ami                    = data.aws_ami.amazon_linux_2023.id
  instance_type          = "t3.micro"
  subnet_id              = aws_subnet.private[0].id
  vpc_security_group_ids = [aws_security_group.app.id]
  iam_instance_profile   = aws_iam_instance_profile.ec2_profile.name
  key_name               = aws_key_pair.deploy.key_name

  root_block_device {
    volume_type           = "gp3"
    volume_size           = 20
    encrypted             = true
    delete_on_termination = true
  }

  user_data = base64encode(<<-EOF
    #!/bin/bash
    set -euo pipefail

    # Update system
    dnf update -y

    # Install Docker
    dnf install -y docker
    systemctl enable --now docker
    usermod -aG docker ec2-user

    # Install Docker Compose
    curl -L "https://github.com/docker/compose/releases/latest/download/docker-compose-$(uname -s)-$(uname -m)" \
      -o /usr/local/bin/docker-compose
    chmod +x /usr/local/bin/docker-compose

    # Install CloudWatch agent
    dnf install -y amazon-cloudwatch-agent

    # Pull and start application
    aws ecr get-login-password --region us-east-1 | \
      docker login --username AWS --password-stdin ${aws_ecr_repository.app.repository_url}
    docker pull ${aws_ecr_repository.app.repository_url}:latest
    docker run -d \
      --name myapp \
      --restart unless-stopped \
      -p 3000:3000 \
      --env-file /etc/myapp/.env \
      ${aws_ecr_repository.app.repository_url}:latest
  EOF
  )

  metadata_options {
    http_tokens = "required"   # require IMDSv2 (security)
  }

  tags = { Name = "myapp-app" }

  lifecycle {
    create_before_destroy = true
  }
}
```

### EC2 Instance Metadata (from inside the instance)

```bash
# IMDSv2 — requires token (more secure than v1)
TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")

# Instance ID
curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/instance-id

# Region
curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/placement/region

# IAM credentials (role name + temp credentials)
curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/iam/security-credentials/
# Returns role name, then:
curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/iam/security-credentials/myapp-ec2-role

# User data script
curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/user-data

# In Node.js: @aws-sdk/ec2-metadata-service
import { MetadataService } from "@aws-sdk/ec2-metadata-service";
const metadata = new MetadataService();
const instanceId = await metadata.request("/latest/meta-data/instance-id", {});
```

### Elastic IPs

By default, an EC2 instance's public IP address is NOT stable — every time you stop and start the instance (not just reboot — actually stop/start), it gets assigned a brand new public IP. That's a problem the moment anything external depends on that IP: a DNS A record, a firewall allow-list at a partner company, a hardcoded IP in a third-party's config.

```
Elastic IP (EIP): a static public IPv4 address you allocate to your AWS
account, which you then attach to (and can detach/reattach between)
EC2 instances. The IP stays the same across stop/start cycles as long
as it stays attached.

aws ec2 allocate-address --domain vpc
# Returns an AllocationId and a PublicIp, e.g. 54.23.45.67

aws ec2 associate-address \
  --instance-id i-1234567890abcdef0 \
  --allocation-id eipalloc-0123456789abcdef0

# Now 54.23.45.67 always points at this instance, even after a stop/start,
# until you explicitly associate it with a different instance.

Cost trap to know for interviews: an Elastic IP is FREE while it's attached
to a running instance. AWS charges for an EIP that is allocated but NOT
attached to anything (to discourage hoarding scarce IPv4 addresses) — a
surprisingly common source of small unexplained AWS bills.

When you DON'T need one: if the instance sits behind an ALB or NLB (the
normal production pattern), the load balancer's DNS name is the stable
endpoint, not the instance's IP — so Elastic IPs are mainly for standalone
instances (a single bastion host, a NAT instance, a small single-server app).
```

## Intermediate Concepts

### EBS Volumes

```bash
# EBS Volume types:
# gp3 (General Purpose SSD):  default, 3000 IOPS baseline, 125 MB/s, up to 16,000 IOPS
# gp2 (Legacy GP SSD):        avoid, IOPS tied to size (3 IOPS/GB)
# io2 Block Express:          mission-critical DBs, 64,000 IOPS, 4,000 MB/s, multi-attach
# st1 (Throughput HDD):       big data, streaming, 500 MB/s
# sc1 (Cold HDD):             archival, lowest cost
# instance store:             physically attached NVMe, ephemeral (lost on stop/terminate)

# List block devices
lsblk

# Format and mount new EBS volume
sudo mkfs -t xfs /dev/xvdf
sudo mkdir /data
sudo mount /dev/xvdf /data

# Persist across reboots (add to /etc/fstab)
sudo echo "/dev/xvdf /data xfs defaults,nofail 0 2" >> /etc/fstab

# Resize root volume (after increasing size in AWS console)
sudo growpart /dev/xvda 1
sudo xfs_growfs -d /

# Create snapshot
aws ec2 create-snapshot \
  --volume-id vol-1234567890 \
  --description "myapp backup $(date +%Y-%m-%d)"
```

## Interview Preparation

**Q1: What is EC2 User Data and when does it run?**
A: User Data is a script (bash, PowerShell, or cloud-init) that runs once when an EC2 instance launches for the first time (not on reboots by default). It runs as root. Use it to: install software, configure the OS, pull Docker images, register with a service, write config files. For updates after launch, use AWS Systems Manager (SSM Run Command or Patch Manager) or a configuration management tool like Ansible. If you need to re-run User Data on reboot, configure cloud-init to run on every boot: add `#cloud-boothook` header or use `cloud-config`. Logs for User Data are at `/var/log/cloud-init-output.log`.

**Q2: What is the difference between stopping and terminating an EC2 instance?**
A: Stop: Instance shuts down, EBS volumes are preserved. You can restart it later. Data on EBS persists. Instance store data IS lost on stop. You're not charged for compute while stopped (still charged for EBS). The public IP changes on restart (unless using Elastic IP). Terminate: Instance is permanently deleted. Root EBS volume deleted by default (`delete_on_termination = true`). Additional EBS volumes may or may not be deleted based on their configuration. To protect against accidental termination, enable termination protection or use a lifecycle policy. Use Stop for instances you'll need again; terminate when done.

**Q3: What is the EC2 Instance Metadata Service and what security issue did v1 have?**
A: IMDS provides instance info from inside the running EC2 instance at `http://169.254.169.254/latest/meta-data/` — instance ID, AZ, IAM role credentials, public IP, user data. IMDSv1 used simple GET requests with no authentication. This was vulnerable to Server-Side Request Forgery (SSRF): an attacker could trick the application into making a request to `http://169.254.169.254/latest/meta-data/iam/security-credentials/role-name` and steal the IAM role's temporary credentials. IMDSv2 requires a PUT request first to get a session token (with a TTL), then all GET requests must include that token header. Prevent SSRF attacks by requiring IMDSv2: `http_tokens = "required"` in Terraform.

## Cheat Sheet

```bash
# EC2 CLI commands
aws ec2 describe-instances --query 'Reservations[].Instances[].{ID:InstanceId,State:State.Name,Type:InstanceType,IP:PublicIpAddress}'
aws ec2 start-instances  --instance-ids i-1234567890
aws ec2 stop-instances   --instance-ids i-1234567890
aws ec2 terminate-instances --instance-ids i-1234567890
aws ec2 describe-instance-status --instance-ids i-1234567890

# Get SSM session (no SSH needed)
aws ssm start-session --target i-1234567890

# Create AMI from running instance
aws ec2 create-image --instance-id i-1234567890 --name "myapp-ami-$(date +%Y%m%d)" --no-reboot

# Key pairs
aws ec2 create-key-pair --key-name mykey --query 'KeyMaterial' --output text > mykey.pem
chmod 400 mykey.pem
ssh -i mykey.pem ec2-user@<public-ip>

# IMDSv2 from inside EC2
TOKEN=$(curl -s -XPUT "http://169.254.169.254/latest/api/token" -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")
curl -s -H "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/instance-id
```
