# Projects That Prove Your Skill

> [!GOALS]
> - Understand what reviewers look for when they open your projects, and what makes a project look like a tutorial.
> - Apply a **finishing standard**: live, runnable, documented, tested, observable, safe, measured and defensible.
> - Choose and build three kinds of projects that prove back-end skill: a **serious data layer**, a **team-grade service**, and a **measured AI feature**.
> - Produce **numbers** that show engineering judgement.
> - Present projects in a README and talk about them in interviews.

## Why this matters

A CV makes claims; projects provide evidence. When a reviewer at a strong company opens your GitHub, they spend perhaps a minute or two deciding one question: does this code look like it came from someone who builds real systems, or from someone who followed a course? They are not counting features. They look for a few specific signals — and their presence or absence often decides whether your experience is believed.

This is especially important if your work experience is hard to show: maintenance of a legacy system, code that belongs to your employer, or no professional experience yet. Well-built projects close that gap. Badly built ones — tutorial clones that only work on the happy path — make it wider. This chapter shows how to build projects that prove skill, using everything in this book; it connects to {{ch:the-job-market}} (what employers screen for) and {{ch:portfolio-and-brand}} (how to present it).

## The simple idea

A project for job hunting is like a carpenter's sample piece. A customer does not look at how many pieces the carpenter has made; they look closely at one: are the joints tight, are the corners finished, does the drawer close smoothly, is the hidden underside as neat as the top? One well-made piece convinces more than twenty rough ones.

> [!ANALOGY]
> A portfolio project is like a carpenter's sample piece: reviewers look closely at the joints and the hidden underside, and one well-finished piece convinces more than twenty rough ones.
>
> **Where the analogy breaks:** a carpenter's sample speaks for itself. Your project will be followed by an interview in which you must explain every decision. A beautiful project you cannot defend — for example one generated by an AI tool you did not understand — does more harm than a modest one you can, because the interview goes badly after the reviewer was impressed.

## The proper definition and key words

A **proof project** is a software project built specifically to demonstrate engineering skill to employers: small enough to finish, realistic enough to need real engineering, deployed, documented and measured.

Key words:

- **Happy path** — the case where everything works; real systems are judged by their failure paths.
- **Finishing standard** — the checklist a project must meet before it counts as done.
- **README** — the front page of a repository explaining the project, decisions and limitations.
- **Architecture diagram** — a picture of the components and their connections.
- **Seed data / demo account** — sample data and a login that let strangers try the project.
- **Failure matrix** — a table of what the system does when each dependency fails.
- **Evidence** — measured numbers, test results and query plans that support claims.

## What reviewers see

### Level 1 — Tutorial signals versus production signals

| Reads as a tutorial | Reads as production experience |
|---|---|
| Works only on the happy path | Handles failures: database down, timeouts, bad input, two users at once |
| Errors return 500, stack traces or "something went wrong" | One clear error format; nothing leaked ({{ch:error-handling}}) |
| No tests, or tests that only check the framework | Real tests including failure cases, running in CI ({{ch:testing}}, {{ch:cicd}}) |
| The generated README, or "run npm start" | A README explaining the problem, design, decisions and limitations |
| Secrets committed, a `.env` in the history | No secrets anywhere; configuration from the environment ({{ch:secrets-manager}}) |
| Every commit message is "update" or "fix" | Readable commits telling how it was built ({{ch:git}}) |
| Nothing measured | Numbers: a query from 400 ms to 12 ms, a cache hit rate, throughput |
| Not deployed | Live at a public URL with a demo account |
| A to-do app or a blog | A realistic domain that needs relationships, search, auth and background work |

### Level 1 — The finishing standard

A project is **not finished** until all of these are true:

| | Requirement |
|---|---|
| **Live** | Deployed at a public HTTPS URL, with seed data and a demo account a stranger can use |
| **Runnable** | `git clone`, then one documented command — tested in an empty folder |
| **Documented** | README with problem, stack, architecture diagram, how to run it, decisions, and honest limitations |
| **Tested** | A real test suite including failure paths, green in CI on every push |
| **Observable** | Structured logs with request IDs, a health check that verifies dependencies, at least one metric ({{ch:logging}}, {{ch:monitoring}}) |
| **Safe** | No secrets in the repository or its history; validation on every input; errors that leak nothing ({{ch:application-security}}) |
| **Measured** | At least three numbers you produced, with how you measured them |
| **Defensible** | You can explain any line without help and name one thing you would do differently |

The **"what I would do differently"** section is not modesty — it is the strongest signal of seniority a README can carry, because it shows you evaluated your own work. "Cache invalidation is TTL-only, so the dashboard can be up to sixty seconds stale; with more time I would invalidate on write" is worth more than any amount of polish.

## Three projects

### Level 2 — Project 1: an API with a serious data layer

**Purpose**: prove you understand data — the area where many candidates are weakest and where interviews probe hardest. **Stack**: Node.js, Express, TypeScript, PostgreSQL ({{ch:express}}, {{ch:postgresql}}).

**Choose a domain** you understand: an inventory tracker for a small shop, a booking system for a clinic, a delivery dispatch tool. It must need relationships, search, authentication and background work, and be small enough to finish.

**It must contain:**

- **A schema you designed and can defend**: real foreign keys, `CHECK` constraints, deliberate `ON DELETE` behaviour, versioned migrations that run from empty ({{ch:database-design}}, {{ch:normalization}}).
- **Indexes with evidence**: several slow queries with `EXPLAIN ANALYZE` before and after, saved in the repository ({{ch:indexes}}).
- **Transactions where needed**, with a race condition you reproduced and the fix you chose ({{ch:transactions}}).
- **Full-text search in PostgreSQL** itself, rather than a second system added too early.
- **Pagination that stays fast**, and a note on what would change at a million rows ({{ch:query-optimization}}).

**Numbers to produce**: the before-and-after time of your slowest query; an N+1 problem found and fixed, with query counts; rows seeded and query times at that volume.

### Level 3 — Project 2: a team-grade service

**Purpose**: prove you can build software the way strong teams do — structure, tests, background processing, caching and failure handling. **Stack**: NestJS, TypeScript, PostgreSQL, Redis, a job queue, Docker ({{ch:nestjs-basics}}, {{ch:nestjs-advanced}}). Rebuilding Project 1's domain properly is a good choice: you can explain concretely what the first version got wrong.

**It must contain:**

- **Modules with deliberate boundaries**, each exporting as little as possible.
- **The full request pipeline**: validation on every input, a role guard, an interceptor for timing, one global exception filter producing one error shape.
- **Authentication and role-based authorisation**, with refresh-token rotation and a written justification of sessions versus tokens ({{ch:authentication}}, {{ch:jwt}}).
- **A real test suite**: unit tests for logic, integration tests against a throwaway database, end-to-end tests for every endpoint including 400 and 401 cases.
- **Redis doing two jobs**: a measured cache on the most expensive read path with a written invalidation strategy, and sessions or real-time fan-out ({{ch:redis}}, {{ch:caching}}).
- **A queue with a separate worker**: retries with backoff, a dead-letter queue, and **idempotent consumers proven by delivering a message twice** ({{ch:queues}}).
- **Real-time updates** over WebSockets, authenticated, working across two instances ({{ch:websockets}}).
- **Resilience**: timeouts on every outbound call, a circuit breaker, and a **failure matrix** describing what happens when each dependency is down ({{ch:distributed-systems}}).
- **Containers and CI/CD**: lint, test against a service database, build the image, deploy on merge ({{ch:docker}}, {{ch:github-actions}}).

**Numbers to produce**: cache hit rate and latency before and after; queue throughput; test count and coverage of failure paths; container image size after a multi-stage build.

The **failure matrix** is often the most impressive part: take Redis down and show that the service degrades rather than dies. Few candidates have thought about it, and it makes for an interview conversation you can lead.

### Level 3 — Project 3: a measured AI feature

**Purpose**: show you can build modern features responsibly. Many candidates have a retrieval demo; very few can say how often it retrieves the right source, what each answer costs, or what happens when the model API is down. **Stack**: NestJS or Express, PostgreSQL with pgvector, an LLM API ({{ch:rag}}, {{ch:embeddings-and-vector-databases}}).

**It must contain:**

- **A real document set** you are allowed to use — your notes, a public documentation set, public PDFs.
- **Ingestion** with sensible chunking, metadata and re-indexing on change.
- **Hybrid retrieval** and an answer prompt with citations and an "I don't know" path.
- **An evaluation set** of real questions with the expected sources, and measured retrieval recall and answer quality ({{ch:building-ai-products}}).
- **Cost and latency per answer**, measured.
- **Failure handling**: timeouts, a fallback when the model is unavailable, and handling of refusals and truncated output.
- **Security**: keys server-side, documents treated as untrusted, rate limits ({{ch:llm-fundamentals}}).

**Numbers to produce**: retrieval recall@5 on your evaluation set; answer correctness rate; average cost and p95 latency per answer.

## Presenting projects

### Level 3 — The README

A strong README answers, in order:

1. **What problem it solves** and for whom, in two sentences, with the live URL and demo account.
2. **Architecture**: a diagram and a paragraph ({{ch:software-architecture}}).
3. **How to run it**: one command, plus how to run the tests.
4. **Key decisions** and the alternatives considered: database, authentication, caching, queue.
5. **Numbers**: what you measured and how.
6. **Limitations and what I would do differently.**

### Level 4 — Talking about projects in interviews

Prepare a **twelve-minute walkthrough** you can shorten to two minutes or extend to twenty:

1. **Problem and users** (one minute).
2. **Architecture** — the main components and data flow.
3. **Data model** — the key tables and one decision you can defend.
4. **The hardest problem** — what broke, how you found it, what you chose and why.
5. **Numbers** — what you measured and what changed.
6. **What you would change**.

Then prepare **three-deep answers** for every technology in it ({{ch:how-hiring-works}}). If an interviewer asks about a part you cannot explain, the project works against you — which is why you should write the code yourself and use AI tools only in ways you fully understand ({{ch:learning-and-ai}}).

## From beginner to enterprise

**Level 1–2 — first proof projects.** A realistic domain; the finishing standard; a data-layer project with migrations, indexes and evidence.

**Level 3 — team-grade work.** A structured service with tests, CI/CD, caching, queues, real-time features and a failure matrix; measured numbers; a decision-focused README.

**Level 4 — modern and measured.** An AI feature with evaluations, costs and failure handling; interview walkthroughs and three-deep preparation.

**Level 5 — beyond portfolio projects.** Open-source contributions, real users for your projects, writing about what you built ({{ch:portfolio-and-brand}}).

**Level 6 — professional work.** At work, the same habits — measurement, documentation, failure planning — are what make engineers trusted with larger systems.

## Real-world use cases

### The project that carried the interview

- **Story**: in a deep-dive round, the interviewer opened a candidate's repository and asked about the index evidence file. The candidate showed the query plan before and after, explained why a composite index helped the sort, and what it cost on writes. The rest of the interview became a conversation rather than a quiz.

### The impressive repository that backfired

- **Story**: a candidate's project had Kubernetes manifests, a service mesh and dozens of microservices. Asked why they chose a mesh, they could not explain what it did. The reviewer's note: "complexity without understanding". A smaller, well-understood project would have done better.

## Common mistakes

### Beginner: tutorial clones and to-do apps

**Fix:** a realistic domain with real data needs.

### Beginner: not deployed

**Fix:** live with a demo account.

### Beginner: secrets in the repository

**Fix:** remove from history, rotate, use environment configuration.

### Intermediate: only happy paths

**Fix:** handle and test failures.

### Intermediate: no numbers

**Fix:** measure and document at least three.

### Intermediate: too many unfinished projects

**Fix:** finish two or three to the standard.

### Production: code you cannot explain

**Fix:** write it yourself; understand everything you include.

## Debugging and troubleshooting

- **Reviewers do not open your projects**: link them clearly on your CV with one-line descriptions and the live URL ({{ch:the-cv}}).
- **The demo is down when they look**: health checks, monitoring and a cheap but reliable host; check before applying.
- **"Runs on my machine" only**: test the one-command set-up in an empty folder or a fresh container.
- **Interviewers do not ask about your projects**: mention them early in your introduction and when answering questions.

## Security summary

- **No secrets** in code or history; rotate anything ever committed.
- **Demo accounts** with limited permissions and resettable data.
- **Rate limits and cost limits**, especially on AI features and anything sending email.
- **Do not use your employer's code or data** in personal projects.

## How a senior engineer thinks about this

- **Depth over breadth.** Two finished, defended projects beat ten demos.
- **Failure handling is the signal.** Anyone can build the happy path.
- **Numbers make claims believable.**
- **Explain decisions and limits.** Judgement is what employers are hiring.

## Exercises

### Exercise 1 — Audit a project

**Objective:** practise the finishing standard.
**What to do:** take one of your projects and score it against the eight requirements of the finishing standard. List what is missing.

<details>
<summary>Show the solution</summary>

Create a table with the eight rows (live, runnable, documented, tested, observable, safe, measured, defensible), mark each yes or no with evidence ("CI badge green", "no tests for 401 paths"), and write the next action for each "no". Typical gaps are failure-path tests, a decisions section, measured numbers and a health check that checks dependencies. Fix those before adding any new features.

</details>

### Exercise 2 — Write the decisions section

**Objective:** practise explaining choices.
**What to do:** write three decision entries for a booking-system API.

<details>
<summary>Show the solution</summary>

- **PostgreSQL over MongoDB**: bookings, clinics and patients are relational and need transactions to prevent double booking; an exclusion constraint on time ranges prevents overlaps in the database itself ({{ch:database-design}}).
- **Short-lived access tokens with rotating refresh tokens over server sessions**: the API serves a mobile app; refresh tokens are stored hashed and rotated, so a stolen one is detected on reuse ({{ch:jwt}}).
- **A queue for reminder messages**: sending SMS in the request would slow bookings and fail when the provider is down; a worker retries with backoff and records sends idempotently ({{ch:queues}}).

Each entry names the alternative and why it lost.

</details>

### Exercise 3 — Prepare the walkthrough

**Objective:** practise presenting.
**What to do:** write the outline of a two-minute version of your best project's walkthrough.

<details>
<summary>Show the solution</summary>

"I built [name], a [domain] system for [users], live at [URL]. It's a NestJS API with PostgreSQL, Redis and a worker for background jobs, deployed with Docker and GitHub Actions. The part I'm proudest of is [hard problem — e.g. preventing double bookings], which I solved with [approach] after reproducing the race condition in a test. I measured [number — e.g. availability search from 600 ms to 25 ms with a composite index]. If I built it again, I'd [one honest change]."

Practise it aloud until it fits two minutes, and prepare to go deeper on any sentence.

</details>

## Summary

Projects are your evidence. Reviewers look for production signals — handled failures, real tests in CI, decision-focused READMEs, no secrets, readable commits, measured numbers, a live deployment — and see tutorial signals as weaknesses. A project is finished only when it is **live, runnable, documented, tested, observable, safe, measured and defensible**, including an honest "what I would do differently".

Three projects prove back-end skill: an **API with a serious data layer** (defended schema, index evidence, transactions, search, pagination), a **team-grade service** (modules, pipeline, authentication, real tests, Redis, queues with idempotent workers, real-time updates, resilience with a failure matrix, containers and CI/CD), and a **measured AI feature** (retrieval with citations, an evaluation set, cost and latency, failure handling and security). Present each with a structured README and a walkthrough you can shorten or extend, prepare three-deep answers for every technology, and include only code you can explain.

## Key terms

- **Proof project** — A project built to demonstrate engineering skill.
- **Happy path** — The scenario in which nothing goes wrong.
- **Failure path** — Behaviour when inputs are invalid or dependencies fail.
- **Finishing standard** — The checklist a project must meet to count as done.
- **README** — The document introducing a repository.
- **Demo account** — A login that lets reviewers try a deployed project.
- **Seed data** — Sample data loaded for demonstration and testing.
- **Failure matrix** — A table of system behaviour for each dependency failure.
- **Evidence file** — Saved measurements such as query plans before and after a change.
- **Project walkthrough** — A structured explanation of a project for interviews.
