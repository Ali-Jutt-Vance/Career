# ORMs: Databases Through Code

> [!GOALS]
> - Explain what an **ORM** (object–relational mapper) is, the problem it solves, and the "impedance mismatch" between objects and tables.
> - Compare the spectrum of tools: raw SQL drivers, **query builders**, and full ORMs.
> - Recognise the patterns ORMs implement: **active record**, **data mapper**, repositories, unit of work and identity maps.
> - Use an ORM well: typed schemas, generated SQL you can inspect, relations, transactions and migrations.
> - Avoid the classic traps: **N+1 queries** from lazy loading, over-fetching, hidden queries, unsafe raw SQL and leaky abstractions.
> - Choose the right tool for a project and know when to drop down to SQL.

## Why this matters

Most back-end code does not send SQL strings directly. It uses an **ORM** or a query builder: `prisma.order.findMany(...)`, `orderRepository.save(order)`, `db.select().from(orders)`. These tools save a great deal of repetitive work — mapping rows to objects, writing similar `INSERT` and `UPDATE` statements, managing migrations — and in TypeScript they catch mistakes at compile time: a misspelt column or a wrong type becomes a red underline instead of a production error.

They also hide what is happening. A line that looks like reading a property can send a query. A loop over 50 orders can send 51 queries. A convenient method can load every column of every row. Engineers who treat the ORM as magic produce exactly the slow pages and surprising bugs from {{ch:query-optimization}}; engineers who understand what it generates get the convenience **and** the performance.

This chapter explains what ORMs do, the patterns behind them, how to use them without losing sight of the SQL, and how to choose between ORMs, query builders and raw SQL. The next two chapters look closely at the two most widely used TypeScript ORMs, {{ch:prisma}} and {{ch:typeorm}}. The examples here use **Drizzle ORM** and the **Kysely** query builder on real PostgreSQL (PGlite), so the generated SQL and query counts shown are exactly what the tools produced.

## The simple idea

Think of a translator between two people who speak different languages. Your application speaks "objects": an `Order` with a `customer` property and a list of `items`. The database speaks "tables": rows in `orders`, `customers` and `order_items` linked by ids. Without a translator, you write every sentence in both languages yourself. An ORM is the translator: you say "give me this customer's orders with their items", and it produces the SQL, runs it, and hands back objects.

A good translator saves enormous effort. A careless one translates word by word — asking the database fifty small questions where one well-phrased question would do — and you only notice when the conversation becomes painfully slow.

> [!ANALOGY]
> An ORM is like a translator between your code's language (objects) and the database's language (tables and SQL): you speak in objects, it phrases the questions in SQL and translates the answers back.
>
> **Where the analogy breaks:** a human translator would notice that you asked the same kind of question fifty times and combine them. An ORM translates exactly what your code asks, when it asks — so code that requests related data one item at a time produces one query per item. You still have to know how to ask good questions.

## The proper definition and key words

An **object–relational mapper (ORM)** is a library that maps database tables to classes or types in application code, generating SQL for common operations so that developers can query and change data through objects.

Key words:

- **Impedance mismatch** — the differences between objects (references, nesting, inheritance) and relational tables (rows, foreign keys, joins).
- **Driver** — the low-level library that connects to the database and sends SQL (such as `pg`).
- **Query builder** — a library for composing SQL with code (methods instead of strings), close to SQL but type-safe and safe from injection: Kysely, Knex, Drizzle's SQL-like API.
- **Entity / model** — a class or type representing a table.
- **Active record** — a pattern where each object knows how to save and load itself (`order.save()`).
- **Data mapper** — a pattern where plain objects are saved and loaded by a separate mapper or repository (`orderRepository.save(order)`).
- **Repository** — an object providing collection-like access to entities (`find`, `save`, `delete`).
- **Unit of work** — tracking changed objects during a business operation and writing all changes together.
- **Identity map** — ensuring each database row is represented by one object per unit of work.
- **Lazy loading** — loading related data only when it is first accessed.
- **Eager loading** — loading related data together with the main data.
- **Migration** — a versioned schema change, often generated by the ORM from the schema definition ({{ch:database-design}}).

## The spectrum of tools

### Level 1 — Raw SQL, query builders and ORMs

| Approach | Example | Strengths | Weaknesses |
|---|---|---|---|
| **Raw SQL with a driver** | `pool.query("SELECT ... WHERE id = $1", [id])` | Full control and every database feature; nothing hidden | Repetitive mapping code; SQL in strings is not type-checked; dynamic queries become string-building |
| **Query builder** | Kysely, Knex, Drizzle's core API | Looks like SQL; composable; typed (Kysely, Drizzle); safe parameters | You still think in tables and joins; less help with relations and object graphs |
| **ORM** | Prisma, TypeORM, MikroORM, Sequelize, Drizzle's relational queries | Fast development for typical CRUD; relations, migrations, typed results | Hidden queries; harder to express complex SQL; performance traps; a large abstraction to learn |

These are not exclusive: almost every serious project uses an ORM or query builder for most queries **and** raw SQL for reports, complex analytics, bulk operations and anything the tool expresses badly.

### Level 2 — What a typed ORM gives you

Here is a schema, inserts and a query in Drizzle, an ORM whose API stays close to SQL:

```ts
import { PGlite } from "@electric-sql/pglite";
import { drizzle } from "drizzle-orm/pglite";
import { pgTable, integer, text, numeric, timestamp } from "drizzle-orm/pg-core";
import { eq, and, gte, desc } from "drizzle-orm";

// The schema is TypeScript: tables, columns and types in one place
const customers = pgTable("customers", {
  id: integer("id").primaryKey().generatedAlwaysAsIdentity(),
  name: text("name").notNull(),
  email: text("email").notNull().unique(),
});
const orders = pgTable("orders", {
  id: integer("id").primaryKey().generatedAlwaysAsIdentity(),
  customerId: integer("customer_id").notNull().references(() => customers.id),
  total: numeric("total", { precision: 10, scale: 2 }).notNull(),
  placedAt: timestamp("placed_at", { withTimezone: true }).notNull(),
});

const client = await PGlite.create();
await client.exec(`
  CREATE TABLE customers (id int GENERATED ALWAYS AS IDENTITY PRIMARY KEY, name text NOT NULL, email text NOT NULL UNIQUE);
  CREATE TABLE orders (id int GENERATED ALWAYS AS IDENTITY PRIMARY KEY, customer_id int NOT NULL REFERENCES customers (id),
                       total numeric(10,2) NOT NULL, placed_at timestamptz NOT NULL);
`);
const db = drizzle(client);

// Inserts return typed rows
const [sara] = await db.insert(customers).values({ name: "Sara Khan", email: "sara@example.com" }).returning();
await db.insert(orders).values([
  { customerId: sara!.id, total: "59.90", placedAt: new Date("2026-09-02T10:00:00Z") },
  { customerId: sara!.id, total: "12.50", placedAt: new Date("2026-10-14T18:20:00Z") },
]);

// A typed query: wrong column names or types are compile errors
const query = db
  .select({ id: orders.id, total: orders.total, customer: customers.name })
  .from(orders)
  .innerJoin(customers, eq(customers.id, orders.customerId))
  .where(and(eq(customers.email, "sara@example.com"), gte(orders.total, "20")))
  .orderBy(desc(orders.placedAt));

console.log(query.toSQL());          // the SQL and parameters the ORM will send
console.log(await query);
```

**Output:**

```text
{
  sql: 'select "orders"."id", "orders"."total", "customers"."name" from "orders" inner join "customers" on "customers"."id" = "orders"."customer_id" where ("customers"."email" = $1 and "orders"."total" >= $2) order by "orders"."placed_at" desc',
  params: [ 'sara@example.com', '20' ]
}
[ { id: 1, total: '59.90', customer: 'Sara Khan' } ]
```

What the tool did:

- **One schema definition** gives table and column names, types and constraints. The result type of the query is inferred: `{ id: number; total: string; customer: string }[]`. Misspelling `customers.nmae` or comparing `total` with a `Date` fails to compile.
- **The generated SQL is ordinary, parameterised SQL** (`$1`, `$2`): values never become part of the query text, so SQL injection is impossible through this API ({{ch:sql}}).
- **`toSQL()`** shows exactly what will be sent — the habit that separates engineers who understand their ORM from those who guess.
- `numeric` columns come back as **strings** (`'59.90'`), because JavaScript numbers cannot represent all decimal values exactly. ORMs differ in how they map types like `numeric`, `bigint` and timestamps; know your tool's choices, especially for money.
- The example creates tables with SQL to stay short; real projects generate them through **migrations** from the schema (Drizzle Kit, Prisma Migrate, TypeORM migrations).

## Patterns behind ORMs

### Level 3 — Active record versus data mapper

**Active record** puts persistence on the object itself:

```ts
// fragment
const order = await Order.findOneBy({ id: 1042 });
order.status = "shipped";
await order.save();                 // the object saves itself
```

It is quick to learn and pleasant for CRUD-heavy applications (Ruby on Rails made it famous; TypeORM and Sequelize support it). The cost: domain objects depend on the database layer, and business logic tends to spread through model classes that are hard to test without a database.

**Data mapper** keeps objects plain and moves persistence into a separate **repository**:

```ts
// fragment
const order = await orderRepository.findById(1042);   // a plain object (or a domain class with no database code)
order.markShipped(now);                               // business rule on the domain object
await orderRepository.save(order);                    // the repository decides how to store it
```

Domain logic can be tested without a database ({{ch:testing}}), and the storage can change behind the repository interface ({{ch:nestjs-basics}}). Prisma, Drizzle, MikroORM and TypeORM's repository API work this way. For larger codebases, data mapper (or repositories wrapping any ORM) usually ages better.

### Level 3 — Unit of work and identity map

Fuller ORMs (TypeORM's entity manager, MikroORM, Hibernate in Java, Entity Framework in .NET) add two more patterns:

- **Identity map**: within one unit of work (usually one request), loading order 1042 twice returns the **same** object, so changes are not split between copies.
- **Unit of work**: the ORM tracks which loaded objects changed and, at "flush" or commit, writes all the necessary `INSERT`, `UPDATE` and `DELETE` statements together, in the right order, inside a transaction.

These reduce boilerplate in complex domain operations. They also mean writes happen at a moment you did not explicitly code — another reason to watch the SQL log.

## Relations and the N+1 trap

### Level 3 — Lazy loading, eager loading, batching

The most frequent ORM performance problem is the **N+1 query problem** ({{ch:query-optimization}}): loading a list, then each item's related data one at a time. ORMs make it easy because relation access looks like property access, and some ORMs **lazy-load** relations automatically. Here are three ways to load ten customers with their orders, counting the queries each sends:

```ts
import { PGlite } from "@electric-sql/pglite";
import { drizzle } from "drizzle-orm/pglite";
import { pgTable, integer, text, numeric } from "drizzle-orm/pg-core";
import { relations, eq, inArray } from "drizzle-orm";

const customers = pgTable("customers", { id: integer("id").primaryKey(), name: text("name").notNull() });
const orders = pgTable("orders", {
  id: integer("id").primaryKey(),
  customerId: integer("customer_id").notNull(),
  total: numeric("total", { precision: 10, scale: 2 }).notNull(),
});
const customersRelations = relations(customers, ({ many }) => ({ orders: many(orders) }));
const ordersRelations = relations(orders, ({ one }) => ({
  customer: one(customers, { fields: [orders.customerId], references: [customers.id] }),
}));

const client = await PGlite.create();
await client.exec(`
  CREATE TABLE customers (id int PRIMARY KEY, name text NOT NULL);
  CREATE TABLE orders (id int PRIMARY KEY, customer_id int NOT NULL REFERENCES customers (id), total numeric(10,2) NOT NULL);
  INSERT INTO customers SELECT i, 'Customer ' || i FROM generate_series(1, 10) i;
  INSERT INTO orders SELECT i, 1 + i % 10, i * 2.5 FROM generate_series(1, 30) i;
`);

let queries = 0;
const db = drizzle(client, {
  schema: { customers, orders, customersRelations, ordersRelations },
  logger: { logQuery: () => { queries++; } },               // count every query the ORM sends
});

// 1. The N+1 pattern: load a list, then load each item's relation separately
queries = 0;
const list = await db.select().from(customers).limit(10);
const withOrders1 = [];
for (const c of list) withOrders1.push({ ...c, orders: await db.select().from(orders).where(eq(orders.customerId, c.id)) });
console.log(`loop over customers:        ${queries} queries`);

// 2. Ask the ORM to load the relation together with the list
queries = 0;
const withOrders2 = await db.query.customers.findMany({ limit: 10, with: { orders: true } });
console.log(`relational query (with):    ${queries} query`);

// 3. Batch manually: the list, then all related rows at once
queries = 0;
const list3 = await db.select().from(customers).limit(10);
const related = await db.select().from(orders).where(inArray(orders.customerId, list3.map((c) => c.id)));
console.log(`batched with IN (...):      ${queries} queries`);

console.log("same data:", withOrders1[0]!.orders.length, withOrders2[0]!.orders.length, related.filter((o) => o.customerId === 1).length);
```

**Output:**

```text
loop over customers:        11 queries
relational query (with):    1 query
batched with IN (...):      2 queries
same data: 3 3 3
```

- The **loop** sends one query for the list and one per customer: 11 queries for 10 customers, and 101 for 100. In ORMs with automatic lazy loading (TypeORM's lazy relations, Sequelize's getters, Active Record in Rails), the same thing happens invisibly when templates or serialisers touch `customer.orders`.
- The **relational query** (`with: { orders: true }`) tells the ORM what will be needed, and it produces a single query (Drizzle uses a lateral join with JSON aggregation in PostgreSQL). Prisma's `include`, TypeORM's `relations` / `leftJoinAndSelect` and MikroORM's `populate` are the equivalents.
- **Batching** with `IN (…)` makes two queries regardless of list size — what DataLoader does in GraphQL ({{ch:graphql}}), and what some ORMs do internally for eager loading.
- All three return the same data. The difference is entirely in how the question was asked.

Two rules prevent most N+1 problems: **say up front which relations you need** (eager loading, includes, joins), and **watch the number of queries per request** in development — log them, or fail tests that exceed a budget.

### Level 3 — Over-fetching

`findMany()` with no `select` returns every column — including large text descriptions, JSON blobs, or a password hash you did not mean to load. Select only what the use case needs; it is faster, keeps sensitive fields out of memory and logs, and enables index-only scans ({{ch:indexes}}). Many ORMs also let you mark columns as excluded by default.

## Writing safely and correctly

### Level 3 — Transactions

ORMs provide transaction helpers that run a callback on one connection and commit or roll back ({{ch:transactions}}):

```ts
// fragment
// Drizzle
await db.transaction(async (tx) => {
  const [order] = await tx.insert(orders).values({ customerId, total, placedAt: new Date() }).returning();
  const updated = await tx.update(products)
    .set({ stock: sql`${products.stock} - ${quantity}` })              // atomic update in the database
    .where(and(eq(products.id, productId), gte(products.stock, quantity)))
    .returning({ id: products.id });
  if (updated.length === 0) throw new OutOfStock(productId);           // rolls back the order too
});

// Prisma (interactive transaction)
await prisma.$transaction(async (tx) => { /* tx.order.create(...), tx.product.update(...) */ });
```

Everything inside must use the transaction object (`tx`), not the global client — using the global client sends that statement **outside** the transaction, a common and silent bug. Note the atomic `stock - quantity` expressed in SQL: ORMs make read–modify–write (`product.stock -= 1; save()`) very easy, and it causes lost updates under concurrency.

### Level 3 — Raw SQL, safely

Every ORM has an escape hatch for raw SQL. Prefer the **tagged-template** forms, which turn interpolated values into parameters:

```ts
// fragment
// Safe: ${email} becomes a parameter ($1)
const rows = await db.execute(sql`SELECT id, name FROM customers WHERE lower(email) = lower(${email})`);
const rows2 = await prisma.$queryRaw`SELECT id FROM customers WHERE email = ${email}`;

// Dangerous: string concatenation, or "unsafe" / "raw" variants with user input
await prisma.$queryRawUnsafe(`SELECT * FROM customers WHERE email = '${email}'`);   // SQL injection
await db.execute(sql.raw(`ORDER BY ${userSuppliedColumn}`));                        // injection through identifiers
```

For dynamic identifiers such as sort columns, map user input through an allow-list (`{ price: products.price, name: products.name }[sort]`).

### Level 3 — Query builders for dynamic queries

Search screens with optional filters are where hand-written SQL turns into fragile string concatenation. A typed query builder composes them cleanly. This Kysely example compiles SQL without connecting to a database, to show what it would send:

```ts
import { Kysely, PostgresAdapter, PostgresIntrospector, PostgresQueryCompiler, DummyDriver } from "kysely";

// Table types: the query builder checks column names and value types against them
interface Database {
  products: { id: number; name: string; category: string; price: string; stock: number; is_active: boolean };
}

// A Kysely instance that only compiles SQL (no database needed)
const db = new Kysely<Database>({
  dialect: {
    createAdapter: () => new PostgresAdapter(),
    createDriver: () => new DummyDriver(),
    createIntrospector: (k) => new PostgresIntrospector(k),
    createQueryCompiler: () => new PostgresQueryCompiler(),
  },
});

type Filters = { search?: string; category?: string; maxPrice?: number; inStockOnly?: boolean; sort?: "price" | "name" };

// Build a query from optional filters, the case where hand-written SQL strings get messy
function searchProducts(f: Filters) {
  let q = db.selectFrom("products").select(["id", "name", "price"]).where("is_active", "=", true);
  if (f.search) q = q.where("name", "ilike", `%${f.search}%`);
  if (f.category) q = q.where("category", "=", f.category);
  if (f.maxPrice !== undefined) q = q.where("price", "<=", String(f.maxPrice));
  if (f.inStockOnly) q = q.where("stock", ">", 0);
  return q.orderBy(f.sort ?? "name").limit(20);
}

for (const filters of [{}, { search: "tea", maxPrice: 5, inStockOnly: true, sort: "price" }] satisfies Filters[]) {
  const { sql, parameters } = searchProducts(filters).compile();
  console.log(sql);
  console.log("  parameters:", parameters);
}
```

**Output:**

```text
select "id", "name", "price" from "products" where "is_active" = $1 order by "name" limit $2
  parameters: [ true, 20 ]
select "id", "name", "price" from "products" where "is_active" = $1 and "name" ilike $2 and "price" <= $3 and "stock" > $4 order by "price" limit $5
  parameters: [ true, '%tea%', '5', 0, 20 ]
```

Each filter adds a condition only when present; every value is a parameter; the sort column can only be one of the allowed column names (the `sort` type restricts it); and column names are checked against the `Database` interface at compile time. In a real application, the `Kysely` instance uses a `PostgresDialect` with a `pg` pool.

## Schemas and migrations

### Level 3 — Where the schema lives

ORMs differ in their **source of truth**:

- **Schema file** (Prisma's `schema.prisma`) — generate the client and migrations from it ({{ch:prisma}}).
- **TypeScript schema** (Drizzle) or **decorated classes** (TypeORM, MikroORM) — generate migrations by comparing code with the database ({{ch:typeorm}}).
- **The database itself** — introspect an existing database to generate types (Kysely with `kysely-codegen`, `prisma db pull`, `drizzle-kit pull`). Useful for existing databases and when SQL migrations are written by hand.

Whatever the source, the rules from {{ch:database-design}} apply: migrations are versioned and reviewed, generated SQL is **read before running** (generators sometimes drop and recreate columns, losing data, when a rename was intended), and changes on live systems follow expand–contract. Avoid "synchronise schema automatically" modes outside local development — they can silently drop columns in production.

## Choosing a tool

### Level 4 — A practical guide

| Situation | Reasonable choice |
|---|---|
| CRUD-heavy TypeScript app, team wants productivity and strong typing | Prisma or Drizzle |
| NestJS project with decorators and repositories already in use | TypeORM or MikroORM (or Prisma via a service) |
| Complex, reporting-heavy queries; team fluent in SQL | Kysely or Drizzle's core API, plus raw SQL |
| Existing database designed outside the application | Introspection-based types (Kysely codegen, Prisma/Drizzle pull) |
| Performance-critical hot paths | Hand-written SQL through the driver or query builder, measured |
| Bulk loads and data migrations | `COPY` and set-based SQL, not ORM loops |

Whichever you choose: enable query logging in development, learn how your tool loads relations, keep transactions explicit, and accept that some queries are better written in SQL. "The ORM can't do it" is a normal reason to write SQL, not a failure.

## From beginner to enterprise

**Level 1–2 — first ORM.** Defining models; basic create, read, update and delete; simple relations; migrations generated by the tool.

**Level 3 — competent use.** Reading generated SQL; eager loading and batching to avoid N+1; selecting only needed fields; transactions with the transaction client; safe raw SQL with tagged templates; reviewing generated migrations.

**Level 4 — production practice.** Repositories around the ORM; query counts monitored per request; atomic updates instead of read–modify–write; query builders for dynamic queries; raw SQL for reports and bulk operations; type mappings for money and big integers understood.

**Level 5 — senior practice.** Choosing tools per context; performance budgets; avoiding vendor lock-in through thin data-access layers; handling multiple databases and read replicas through the data layer ({{ch:replication}}).

**Level 6 — enterprises.** Shared data-access libraries and conventions across teams; schema registries and migration governance; generated clients for many services; data access audited for compliance.

## Real-world use cases

### The slow admin list

- **Symptom**: an admin page listing 50 orders with customer names and item counts takes 2 seconds.
- **Diagnosis**: the ORM's query log shows 101 queries — the template accesses `order.customer` and `order.items.length`, each lazily loaded.
- **Fix**: load customers eagerly with the list (one join) and item counts with a single aggregate query (or the ORM's count include). Three queries; 40 ms.

### Reports in an ORM-based app

- **Situation**: finance needs monthly revenue by category with month-over-month growth.
- **Approach**: a raw SQL query with window functions ({{ch:sql}}), run through the ORM's tagged-template raw API and typed with an explicit result type, in a reporting module — instead of loading thousands of rows into JavaScript and summing them.

## Common mistakes

### Beginner: treating relation properties as free

**Consequence:** N+1 queries. **Fix:** eager loading or batching; query logging.

### Beginner: loading whole tables into memory

`findMany()` and filtering in JavaScript. **Fix:** filter, sort, paginate and aggregate in the database.

### Beginner: never looking at the generated SQL

**Fix:** log queries in development; use `toSQL()`/`compile()` or the ORM's debug output.

### Intermediate: read–modify–write through objects

`product.stock -= qty; await save(product)`. **Consequence:** lost updates under concurrency. **Fix:** atomic updates or locking ({{ch:transactions}}).

### Intermediate: forgetting the transaction client

Using the global client inside a transaction callback. **Fix:** always use `tx`.

### Intermediate: unsafe raw SQL

**Fix:** tagged templates; allow-lists for identifiers.

### Production: automatic schema synchronisation

**Consequence:** dropped columns and data loss. **Fix:** reviewed migrations only.

### Production: trusting generated migrations blindly

**Fix:** read every migration; test on production-like data; follow expand–contract.

## Debugging and troubleshooting

- **A page is slow but no query is slow**: count queries per request — N+1 from lazy loading or loops.
- **Unexpected updates appear in logs**: a unit-of-work ORM flushed changes to objects you modified (perhaps unintentionally) — check what was changed and when the flush happened.
- **Numbers come back as strings**: `numeric` and `bigint` mapping — convert deliberately (decimal libraries for money) rather than with `Number()`.
- **A change in a transaction was not rolled back**: that statement used the global client instead of the transaction client.
- **Generated migration drops a column you renamed**: the generator saw "remove old, add new" — edit the migration to `RENAME COLUMN`, or use the tool's rename prompt.
- **Type errors after schema changes**: regenerate the client/types (`prisma generate`, codegen) and keep generation in the build.

## Security summary

- ORM query APIs **parameterise values** — prefer them over string-built SQL.
- Raw SQL must use **tagged templates**; never pass user input to `…Unsafe` or `sql.raw` functions; allow-list identifiers.
- **Select only needed fields** so sensitive columns (password hashes, tokens) are not loaded or accidentally returned; never return entities directly from APIs ({{ch:nestjs-advanced}}).
- **Mass assignment**: do not pass request bodies straight into `create()`/`update()`; map validated DTOs to allowed fields ({{ch:validation}}).
- Review **generated migrations** like code — they change production data.
- Keep **query logs** free of sensitive parameter values in production.

## How a senior engineer thinks about this

- **An ORM is a SQL generator.** They know what SQL each call produces, and check it.
- **Relations are queries.** Loading strategies are decided deliberately for every list and page.
- **Use the right level for each job.** ORM for everyday CRUD, query builder for dynamic queries, raw SQL for reports and bulk work.
- **Concurrency and transactions are still the developer's responsibility.** The ORM does not make read–modify–write safe.
- **Keep the data layer thin and replaceable.** Repositories and clear boundaries limit how far one tool's quirks spread.

### Exercise 1 — Spot the hidden queries

**Objective:** practise recognising N+1 patterns.
**What to do:** count the queries this code sends for a page of 25 orders, each with 3 items, and rewrite it to use a constant number of queries: `const orders = await db.select().from(ordersTable).limit(25); for (const o of orders) { o.customer = await getCustomer(o.customerId); o.items = await getItems(o.id); for (const i of o.items) i.product = await getProduct(i.productId); }`.

<details>
<summary>Show the solution</summary>

**Count:** 1 (orders) + 25 (customers) + 25 (item lists) + 25 × 3 = 75 (products) = **126 queries**.

**Rewrite (4 queries):**
1. Load the 25 orders.
2. Load their customers with `WHERE id IN (…distinct customer ids…)` — or join customers into query 1, since each order has one customer.
3. Load all items with `WHERE order_id IN (…25 order ids…)`.
4. Load all products with `WHERE id IN (…distinct product ids from the items…)`.

Then assemble the object graph in memory with maps keyed by id. With a relational ORM, the same is one call: `findMany({ limit: 25, with: { customer: true, items: { with: { product: true } } } })` (Drizzle), or `include: { customer: true, items: { include: { product: true } } }` (Prisma). Add a query-count assertion to the endpoint's test so it cannot regress.

2. **Query builder** (or the ORM's query builder) — dynamic conditions composed safely, typed columns, allow-listed sorts.
3. **Raw SQL** (tagged template) — window functions and grouping that ORMs express poorly; typed result interface; maybe a materialised view ({{ch:normalization}}).
4. **Raw SQL / `COPY`** — bulk loading into a staging table, then set-based `INSERT … SELECT`; ORM loops would take hours.
5. **ORM relational query** — eager loading of items and products in one or a few queries; select only the fields the page shows.

</details>

### Exercise 3 — Review the repository code

**Objective:** practise spotting ORM misuse.
**The scenario:** a repository method does `await prisma.$queryRawUnsafe("SELECT * FROM orders WHERE status = '" + status + "' ORDER BY " + sortBy)`. Another method updates stock with `const p = await prisma.product.findUnique({ where: { id } }); await prisma.product.update({ where: { id }, data: { stock: p.stock - qty } })`. A third returns `prisma.user.findMany()` directly from an API endpoint. List the problems and fixes.

<details>
<summary>Show the solution</summary>

1. **SQL injection** through `status` and `sortBy`, plus `SELECT *`. Fix: the ORM's query API (`findMany({ where: { status }, orderBy: { [allowed[sortBy]]: "asc" } })`) or `$queryRaw` tagged template with an allow-listed sort column; select only needed fields.
2. **Lost update** (read–modify–write) and no check for insufficient stock. Fix: atomic `update({ where: { id, stock: { gte: qty } }, data: { stock: { decrement: qty } } })` inside a transaction, and treat "no record updated" as out of stock (Prisma's `updateMany` returns a count for such conditional updates).
3. **Data exposure**: `findMany()` returns every column — including password hashes — and every user. Fix: `select` explicit public fields, paginate, authorise, and map to a response DTO.

</details>

### Exercise 4 — Production scenario: the migration that lost data

**Objective:** practise safe schema changes with ORMs.
**The scenario:** a developer renamed `Customer.phone` to `Customer.phoneNumber` in the ORM schema, generated a migration, and deployed. Customers' phone numbers disappeared. What happened, how do you recover, and how do you prevent it?

<details>
<summary>Show the solution</summary>

**What happened:** the migration generator could not know the field was renamed; it produced `ALTER TABLE customers DROP COLUMN phone; ALTER TABLE customers ADD COLUMN phone_number text;` — deleting the data. Nobody read the generated SQL before deploying.

**Recovery:**
1. Stop further damage (pause the deployment if possible).
2. Restore the lost column's data from a backup using point-in-time recovery into a **separate** database, then copy `id, phone` back into `phone_number` with an `UPDATE … FROM` ({{ch:postgresql}}).
3. Communicate with affected teams; check whether anything (SMS notifications, deliveries) failed meanwhile.

**Prevention:**
- Read every generated migration in code review; look for `DROP` statements.
- Use the tool's rename support (prompted renames) or edit the migration to `ALTER TABLE customers RENAME COLUMN phone TO phone_number;` — or keep the database column name and map the new field name in the ORM.
- For live systems, use expand–contract instead of renames ({{ch:database-design}}).
- Run migrations against a production-like copy in CI, and fail on destructive statements unless explicitly approved.

</details>

## Summary

An **ORM** maps tables to types or classes and generates SQL for common operations, bridging the **impedance mismatch** between objects and relational tables. Tools range from **raw SQL** with a driver (full control, more boilerplate), through typed **query builders** such as Kysely and Drizzle's core API (SQL-shaped, composable, safe parameters), to full **ORMs** such as Prisma, TypeORM and MikroORM (relations, migrations, productivity, hidden queries). Most real projects combine an ORM or builder with raw SQL where it fits better.

ORMs implement patterns: **active record** (objects save themselves), **data mapper** with **repositories** (plain objects, separate persistence — easier to test and evolve), and in fuller ORMs the **unit of work** and **identity map**. Their benefits — one schema, typed results, parameterised SQL, migrations — come with traps: **N+1 queries** from lazy loading or loops (fix with eager loading, relational queries or batching, and watch query counts), **over-fetching**, read–modify–write lost updates, statements accidentally run outside the **transaction client**, unsafe raw SQL (use tagged templates and allow-lists), and destructive generated migrations (read them; follow expand–contract).

Choose tools by context — productivity for CRUD, query builders for dynamic queries, raw SQL for reports and bulk work — and always know the SQL your code sends.

## Key terms

- **ORM (object–relational mapper)** — A library mapping database tables to code types or classes and generating SQL.
- **Impedance mismatch** — The structural differences between object models and relational tables.
- **Database driver** — The low-level library that connects to a database and executes SQL.
- **Query builder** — A library for composing SQL queries with code instead of strings.
- **Entity (model)** — A class or type representing a database table.
- **Active record** — A pattern where objects contain methods to load and save themselves.
- **Data mapper** — A pattern where separate mappers or repositories load and save plain objects.
- **Repository** — An object offering collection-like methods to find and save entities.
- **Unit of work** — Tracking changes during an operation and writing them together.
- **Identity map** — Keeping one object per database row within a unit of work.
- **Lazy loading** — Loading related data only when it is accessed.
- **Eager loading** — Loading related data together with the main query.
- **Relational query** — An ORM query that loads an entity together with specified relations.
- **Over-fetching** — Loading more columns or rows than needed.
- **Transaction client** — The ORM object that runs statements within a specific transaction.
- **Tagged template (SQL)** — A template literal syntax that turns interpolated values into query parameters.
- **Schema introspection** — Generating types or models by reading an existing database's structure.
- **Generated migration** — A migration produced by comparing a schema definition with the database.
- **Schema synchronisation** — An ORM mode that changes the database to match models automatically, unsafe in production.
- **Drizzle ORM** — A TypeScript ORM with a SQL-like typed API and relational queries.
- **Kysely** — A type-safe SQL query builder for TypeScript.
- **Prisma** — A schema-first TypeScript ORM with a generated client.
- **TypeORM** — A decorator-based TypeScript ORM supporting active record and data mapper patterns.
