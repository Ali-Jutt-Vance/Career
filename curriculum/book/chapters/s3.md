# S3: Storing Files

> [!GOALS]
> - Explain object storage and how S3 differs from a file system and a database.
> - Understand **buckets**, **objects**, **keys**, and S3's durability and consistency.
> - Keep data private with **Block Public Access**, bucket policies and encryption.
> - Let browsers upload and download directly with **pre-signed URLs**.
> - Use **storage classes**, **versioning**, **lifecycle rules** and **event notifications**.
> - Avoid the classic mistakes: public buckets, trusting client file names, and runaway storage costs.

## Why this matters

Almost every application stores files: product images, user avatars, invoices, exports, backups, logs, build artifacts. Keeping them on a server's disk causes problems straight away — the second server cannot see them, the disk fills up, and the files disappear when the instance is replaced ({{ch:ec2}}). Keeping them in the database makes it huge and slow.

**Amazon S3 (Simple Storage Service)** is where files go instead. It stores practically unlimited data, is designed for 99.999999999% (eleven nines) durability by keeping copies across several availability zones, and serves files over HTTPS to servers and browsers anywhere. It is also the foundation of data lakes, static websites, backups and the content delivery behind CloudFront ({{ch:cloudfront}}).

S3 is also famous for leaks: misconfigured public buckets have exposed millions of customer records. This chapter covers how to use S3 well — including the file-upload design from {{ch:file-uploads}} with direct-to-S3 uploads — and how to keep it private.

## The simple idea

S3 is like an enormous, extremely reliable cloakroom. You hand in an item, and you get a ticket with a unique label. Later, anyone who shows the right label — and is allowed to — gets the exact item back. The cloakroom does not care what is in the bag; it never opens it or changes part of it. To change something, you hand in a whole new item under the same label.

> [!ANALOGY]
> S3 is like a huge, reliable cloakroom: you hand in a whole item, get a label (the key), and later collect exactly that item with the label.
>
> **Where the analogy breaks:** a cloakroom has an attendant who checks your ticket at the counter. In S3, access rules are something **you** configure — and a single wrong setting can turn the cloakroom into an open room where anyone on the internet who guesses or finds a label can take any item.

## The proper definition and key words

**Amazon S3** is an object storage service. Data is stored as **objects** in **buckets**; each object is identified by a **key**, contains data of up to 5 TB plus metadata, and is read and written as a whole through an HTTP API.

Key words:

- **Bucket** — a container for objects, with a globally unique name, in one region.
- **Object** — the stored data plus metadata (content type, custom metadata, tags).
- **Key** — the object's name within the bucket, such as `uploads/user-81/7f3c9a2e.jpg`. The slashes look like folders but are just part of the name; a **prefix** is the beginning of keys.
- **Block Public Access** — account- and bucket-level settings that stop anything from being made public.
- **Bucket policy** — a resource-based policy deciding who may do what in the bucket ({{ch:iam}}).
- **Pre-signed URL** — a URL signed with credentials that grants temporary access to one operation on one object.
- **Storage class** — the price and access trade-off: Standard, Intelligent-Tiering, Standard-IA, Glacier tiers.
- **Versioning** — keeping every version of each object.
- **Lifecycle rule** — automatically moving or deleting objects by age or prefix.
- **Event notification** — a message sent when objects are created or deleted.
- **Multipart upload** — uploading a large object in parts, in parallel and resumably.

## The basics

### Level 1 — Buckets, objects and keys

- **Bucket names** are global across all AWS accounts and appear in URLs, so they are often prefixed with the company and environment: `cornershop-production-uploads`.
- **Keys** are designed by you. Put the things you will list or manage together under common prefixes: `uploads/user-81/…`, `invoices/2026/11/…`, `exports/…`. Lifecycle rules, permissions and event filters all work by prefix.
- **Objects are immutable**: you replace the whole object, never edit part of it. Appending a line to a log file means writing a new object.
- **Consistency**: S3 has strong read-after-write consistency — after a successful write, every read returns the new object, and listings include it.
- **Operations** are HTTP requests: `PUT` (upload), `GET` (download, including byte ranges), `HEAD` (metadata), `DELETE`, `LIST` (keys by prefix, paginated).

From TypeScript, the SDK wraps these calls:

```ts
// fragment
import { S3Client, PutObjectCommand, GetObjectCommand, ListObjectsV2Command } from "@aws-sdk/client-s3";

const s3 = new S3Client({ region: "eu-west-2" });   // credentials come from the role

await s3.send(new PutObjectCommand({
  Bucket: "cornershop-production-uploads",
  Key: `invoices/2026/11/${orderId}.pdf`,
  Body: pdfBuffer,
  ContentType: "application/pdf",
}));

const listing = await s3.send(new ListObjectsV2Command({
  Bucket: "cornershop-production-uploads",
  Prefix: "invoices/2026/11/",
}));
console.log(listing.KeyCount, "invoices this month");
```

### Level 2 — Keeping buckets private

Buckets are private by default, and **Block Public Access** is on by default for new buckets. Keep it on at the **account** level. Most leaks happened when someone turned it off "temporarily" or added a policy with `"Principal": "*"`.

- **Who may access**: your application's role, through its identity policy ({{ch:iam}}); other accounts or services through the **bucket policy**.
- **Serve public files through CloudFront**, not public buckets: CloudFront reads the private bucket with Origin Access Control, adds caching and HTTPS on your domain, and the bucket stays private ({{ch:cloudfront}}).
- **Object ownership**: keep the "bucket owner enforced" setting so ACLs are disabled and only policies control access.
- **Encryption at rest** is automatic (SSE-S3). For stricter control — separate permissions and audit for decrypting — use **SSE-KMS** with a customer-managed key.
- **Require TLS** with a bucket policy condition `aws:SecureTransport` — and in sensitive environments, restrict access to your VPC endpoint.

A bucket policy enforcing HTTPS:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "DenyInsecureTransport",
    "Effect": "Deny",
    "Principal": "*",
    "Action": "s3:*",
    "Resource": ["arn:aws:s3:::cornershop-production-uploads", "arn:aws:s3:::cornershop-production-uploads/*"],
    "Condition": { "Bool": { "aws:SecureTransport": "false" } }
  }]
}
```

Here `"Principal": "*"` is safe because the effect is **Deny** — it applies the rule to everyone.

## Uploads and downloads from browsers

### Level 3 — Pre-signed URLs

Uploading through your API means every byte passes through your servers: slow, memory-hungry and expensive at scale. A **pre-signed URL** lets the browser talk to S3 directly, while your API still decides **who** may upload **what**, **where**, and **for how long** ({{ch:file-uploads}}):

```text
 browser ── 1. "I want to upload a JPEG" ──► API (checks login, size, type, quota)
 browser ◄─ 2. pre-signed PUT URL (5 minutes, fixed key) ── API
 browser ── 3. PUT file directly ──► S3
 S3 ─────── 4. event "object created" ──► worker (scan, resize, record in database)
```

The API signs the URL **locally** with its role's credentials — creating one is just a computation, with no request to AWS:

```ts
import { S3Client, PutObjectCommand, GetObjectCommand } from "@aws-sdk/client-s3";
import { getSignedUrl } from "@aws-sdk/s3-request-presigner";

// Signing happens locally with the credentials: no network call is needed to create the URL.
// (Fixed example credentials and a fixed clock keep this output the same on every run;
//  in production the role's temporary credentials are used, as in the IAM chapter.)
const s3 = new S3Client({
  region: "eu-west-2",
  credentials: { accessKeyId: "AKIAIOSFODNN7EXAMPLE", secretAccessKey: "wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY" },
  requestChecksumCalculation: "WHEN_REQUIRED",   // no checksum of an empty body baked into upload URLs
});
const signingDate = new Date("2026-11-20T10:00:00Z");

// The API decides the key (never trust the browser's file name) and the content type.
const key = "uploads/user-81/7f3c9a2e.jpg";
const uploadUrl = await getSignedUrl(
  s3,
  new PutObjectCommand({ Bucket: "cornershop-uploads", Key: key, ContentType: "image/jpeg" }),
  { expiresIn: 300, signingDate, signableHeaders: new Set(["content-type"]) },  // the browser must send this exact type
);
const downloadUrl = await getSignedUrl(
  s3,
  new GetObjectCommand({ Bucket: "cornershop-uploads", Key: key, ResponseContentDisposition: 'attachment; filename="receipt.jpg"' }),
  { expiresIn: 60, signingDate },
);

for (const [label, raw] of [["upload (PUT)", uploadUrl], ["download (GET)", downloadUrl]] as const) {
  const url = new URL(raw);
  console.log(`${label}: ${url.origin}${url.pathname}`);
  for (const name of ["X-Amz-Algorithm", "X-Amz-Credential", "X-Amz-Date", "X-Amz-Expires", "X-Amz-SignedHeaders"]) {
    console.log(`  ${name.padEnd(20)} ${url.searchParams.get(name)}`);
  }
  console.log(`  X-Amz-Signature      ${url.searchParams.get("X-Amz-Signature")!.length} hex characters`);
}

// The expiry is part of what is signed: a URL for 7 days has a completely different signature,
// so editing X-Amz-Expires in a 5-minute URL leaves a signature that no longer matches (S3 answers 403).
const weekUrl = await getSignedUrl(
  s3,
  new PutObjectCommand({ Bucket: "cornershop-uploads", Key: key, ContentType: "image/jpeg" }),
  { expiresIn: 604800, signingDate, signableHeaders: new Set(["content-type"]) },
);
const sig = (u: string) => new URL(u).searchParams.get("X-Amz-Signature")!;
console.log("5-minute and 7-day URLs share a signature:", sig(uploadUrl) === sig(weekUrl));
```

**Output:**

```text
upload (PUT): https://cornershop-uploads.s3.eu-west-2.amazonaws.com/uploads/user-81/7f3c9a2e.jpg
  X-Amz-Algorithm      AWS4-HMAC-SHA256
  X-Amz-Credential     AKIAIOSFODNN7EXAMPLE/20261120/eu-west-2/s3/aws4_request
  X-Amz-Date           20261120T100000Z
  X-Amz-Expires        300
  X-Amz-SignedHeaders  content-type;host
  X-Amz-Signature      64 hex characters
download (GET): https://cornershop-uploads.s3.eu-west-2.amazonaws.com/uploads/user-81/7f3c9a2e.jpg
  X-Amz-Algorithm      AWS4-HMAC-SHA256
  X-Amz-Credential     AKIAIOSFODNN7EXAMPLE/20261120/eu-west-2/s3/aws4_request
  X-Amz-Date           20261120T100000Z
  X-Amz-Expires        60
  X-Amz-SignedHeaders  host
  X-Amz-Signature      64 hex characters
5-minute and 7-day URLs share a signature: false
```

- The URL carries the **signature** (an HMAC computed from the method, bucket, key, signed headers, date and expiry with the secret key) and the access key ID — **never the secret key**. S3 recomputes the signature; if anything signed was changed, or the URL has expired, it refuses with `403`.
- The expiry is part of what is signed: a 7-day URL has a completely different signature, so nobody can extend a 5-minute URL by editing it.
- `signableHeaders` adds **`content-type`** to the signed headers, so the browser must upload with exactly `image/jpeg`. By default the SDK signs only `host`, and a client could upload any content type under your key.
- Newer SDK versions add a checksum for the request body to signed upload URLs by default. A URL created before the file exists would carry the checksum of an empty body and the browser's upload would fail. `requestChecksumCalculation: "WHEN_REQUIRED"` turns that off.
- The **API chooses the key** — a random name in the user's prefix — and never trusts the browser's file name, which can contain path tricks or overwrite other files. The download URL sets `Content-Disposition` so the browser saves the file with a friendly name.
- A pre-signed URL can do **no more than the signer's role**, and stops working when the role's temporary credentials expire, even if its own expiry is later.
- To enforce a **maximum size**, use a **pre-signed POST** (`@aws-sdk/s3-presigned-post`) with a `content-length-range` condition. A pre-signed PUT cannot limit the size, so check the object afterwards.
- **Never treat an uploaded file as safe** until it has been checked: verify its real type and size, scan it, and serve user files from a separate domain ({{ch:application-security}}).

### Level 3 — Large files

Files over about 100 MB should use **multipart upload**: parts are uploaded in parallel, a failed part is retried alone, and uploads can resume. `@aws-sdk/lib-storage`'s `Upload` class does this automatically on servers. Add a lifecycle rule to abort incomplete multipart uploads, whose parts otherwise keep costing money.

## Managing data over time

### Level 3 — Storage classes and lifecycle rules

| Class | For | Notes |
|---|---|---|
| **Standard** | Frequently accessed data | Default; milliseconds |
| **Intelligent-Tiering** | Unknown or changing access patterns | Moves objects between tiers automatically for a small monitoring fee |
| **Standard-IA / One Zone-IA** | Infrequently accessed, needed quickly | Cheaper storage, a retrieval fee, a minimum storage duration |
| **Glacier Instant / Flexible / Deep Archive** | Archives and compliance | Very cheap storage; retrieval from milliseconds (Instant) to hours (Deep Archive) |

**Lifecycle rules** apply these automatically by prefix and age:

```json
{
  "Rules": [
    { "ID": "invoices-archive", "Filter": { "Prefix": "invoices/" }, "Status": "Enabled",
      "Transitions": [{ "Days": 90, "StorageClass": "STANDARD_IA" }, { "Days": 365, "StorageClass": "GLACIER_IR" }],
      "Expiration": { "Days": 2555 } },
    { "ID": "exports-cleanup", "Filter": { "Prefix": "exports/" }, "Status": "Enabled",
      "Expiration": { "Days": 7 } },
    { "ID": "abort-incomplete-uploads", "Filter": {}, "Status": "Enabled",
      "AbortIncompleteMultipartUpload": { "DaysAfterInitiation": 3 } }
  ]
}
```

Invoices move to cheaper classes as they age and are deleted after seven years (a typical legal retention period); temporary exports disappear after a week. Without rules like these, storage costs only ever grow ({{ch:cost-optimization}}).

### Level 3 — Versioning, replication and protection

- **Versioning** keeps every version of each object. An overwrite or delete creates a new version or a "delete marker" instead of destroying data, so mistakes and ransomware can be undone. Add lifecycle rules to expire old versions after some time.
- **Object Lock** (write once, read many) prevents deletion for a retention period, even by administrators — used for compliance and backup protection.
- **Replication** copies objects to another region or account automatically, for disaster recovery or data separation.
- **MFA delete** and strict policies protect critical buckets such as backups and Terraform state ({{ch:terraform}}).

### Level 4 — Events and processing

S3 can send **event notifications** when objects are created or deleted — to SQS, SNS, Lambda or EventBridge:

- A new upload in `uploads/` triggers a worker that scans it, creates thumbnails and records it in the database ({{ch:lambda}}, {{ch:sns-sqs}}).
- Events can be delivered **more than once** and sometimes out of order. Make processing **idempotent** (processing the same event twice has the same result) ({{ch:queues}}).
- Avoid loops: a function that writes its output to the same prefix that triggers it will trigger itself for ever. Write outputs to a different prefix or bucket.

## From beginner to enterprise

**Level 1–2 — first buckets.** Buckets and keys; uploading and listing with the SDK; Block Public Access on; roles instead of keys; default encryption.

**Level 3 — application storage.** Pre-signed URLs for direct uploads and downloads with server-chosen keys; multipart uploads; lifecycle rules and storage classes; versioning; serving public content through CloudFront.

**Level 4 — production data.** Event-driven processing with idempotent workers; SSE-KMS for sensitive data; TLS-only and VPC-endpoint policies; replication and Object Lock for backups; access logging.

**Level 5 — senior practice.** Key and prefix design for permissions, lifecycle and analytics; cost analysis with Storage Lens; data classification and retention policies.

**Level 6 — enterprises.** Data lakes on S3 with central governance (Lake Formation, Athena); organisation-wide guardrails against public buckets; cross-account backup vaults.

## Real-world use cases

### Product images for a shop

- **Design**: the admin interface gets a pre-signed PUT URL for `products/originals/<uuid>.jpg`; an S3 event triggers a resize function writing to `products/sized/`; CloudFront serves `sized/` with long cache times; versioning protects against accidental overwrites.

### The leaked bucket

- **What happened**: a contractor turned off Block Public Access to share a database export "for an hour" and forgot. Search engines for open buckets found it within days.
- **Prevention**: account-level Block Public Access enforced by an organisation policy; exports shared with short-lived pre-signed URLs; AWS Config rules and Access Analyzer alerting on any public bucket.

## Common mistakes

### Beginner: public buckets for serving files

**Consequence:** data leaks and no control. **Fix:** private buckets, CloudFront or pre-signed URLs.

### Beginner: uploading through the API server

**Consequence:** slow uploads and overloaded servers. **Fix:** pre-signed URLs.

### Beginner: using the client's file name as the key

**Consequence:** overwrites, path tricks, leaked personal names. **Fix:** server-generated keys.

### Intermediate: no lifecycle rules

**Consequence:** ever-growing bills from old exports, versions and abandoned multipart parts. **Fix:** lifecycle rules per prefix.

### Intermediate: long-lived pre-signed URLs

**Consequence:** links that keep working after they are shared or leaked. **Fix:** minutes, not days.

### Production: non-idempotent event processing

**Consequence:** duplicate thumbnails, double charges. **Fix:** idempotent handlers keyed on object key and version.

### Production: no versioning on important buckets

**Consequence:** permanent loss from an accidental delete. **Fix:** versioning, replication, Object Lock for backups.

## Debugging and troubleshooting

- **403 AccessDenied**: check the role's identity policy, the bucket policy, Block Public Access, the KMS key policy (for SSE-KMS objects) and whether the object exists — S3 returns 403 instead of 404 when the caller cannot list the bucket.
- **SignatureDoesNotMatch on pre-signed uploads**: the browser sent a different `Content-Type` or extra signed headers than were signed, the clock is wrong, or a checksum parameter is included.
- **CORS errors in the browser**: the bucket needs a CORS configuration allowing your site's origin, the `PUT` method and the headers you send.
- **Slow listing**: listing millions of keys is slow; keep an index in your database, or use S3 Inventory.
- **Unexpected costs**: Storage Lens and Cost Explorer by storage class and request type; check old versions and incomplete uploads.

## Security summary

- **Block Public Access** at the account level; no `"Principal": "*"` allows.
- **Least-privilege roles** scoped to prefixes; no access keys.
- **Encryption** by default; SSE-KMS for sensitive data; TLS required.
- **Pre-signed URLs** with short expiry, server-chosen keys, signed content types and size limits.
- **Treat uploads as untrusted** until validated and scanned.
- **Versioning, replication and Object Lock** for important data; access logs and CloudTrail data events for sensitive buckets.

## How a senior engineer thinks about this

- **Files belong in object storage**, not on servers or in databases.
- **Private by default, public through a controlled layer.** CloudFront and pre-signed URLs, never public buckets.
- **Design keys deliberately.** Prefixes drive permissions, lifecycle and events.
- **Plan the data's whole life.** Creation, access, archive and deletion.
- **Events are at-least-once.** Idempotent processing, no loops.

### Exercise 2 — Review the upload design

**Objective:** practise secure uploads.
**The design:** the API returns a pre-signed PUT URL valid for 7 days for the key `uploads/${req.body.filename}`; the uploaded files are served from the same bucket, which is public, on the main domain.

<details>
<summary>Show the solution</summary>

1. **7 days** is far too long — use minutes.
2. **Client-chosen key**: overwrites and path tricks — generate a random key in the user's prefix.
3. **No content-type or size control**: sign the content type and use a pre-signed POST with a size range.
4. **Public bucket**: keep it private; serve through CloudFront or pre-signed GET URLs.
5. **Same domain**: an uploaded HTML or SVG file could run scripts in your site's origin — serve user content from a separate domain with safe headers, after validation and scanning.

</details>

### Exercise 3 — Production scenario: the growing bill

**Objective:** practise cost and data hygiene.
**The scenario:** S3 costs have tripled in a year. The main bucket has versioning on, holds 40 TB, and nobody knows what most of it is. What do you do?

<details>
<summary>Show the solution</summary>

1. **Measure**: Storage Lens and Inventory by prefix, storage class, object age and noncurrent versions; check incomplete multipart uploads.
2. **Typical findings**: old noncurrent versions never expired; temporary exports never deleted; logs in Standard; abandoned multipart parts.
3. **Lifecycle rules**: expire noncurrent versions after, say, 30 days; expire exports; move logs and old invoices to IA or Glacier tiers; abort incomplete uploads after 3 days.
4. **Intelligent-Tiering** for large data with unknown access patterns.
5. **Ownership**: tags and prefixes per team, so each team sees its own costs.
6. Check retention requirements with legal or compliance before deleting anything.

</details>

## Summary

**S3** is AWS's object storage: practically unlimited, highly durable storage of **objects** in **buckets**, each identified by a **key** you design, read and written whole over HTTP, with strong read-after-write consistency. Files belong here rather than on servers or in databases.

Keep data private: **Block Public Access** at the account level, least-privilege **roles** and **bucket policies**, encryption (SSE-S3 or SSE-KMS), TLS required, and public content served through **CloudFront**. Browsers upload and download directly with **pre-signed URLs** — signed locally, short-lived, for a server-chosen key, with the content type signed and sizes limited through pre-signed POST — and uploaded files are treated as untrusted until checked. Large files use **multipart uploads**.

**Storage classes** and **lifecycle rules** move and delete data by prefix and age; **versioning**, **replication** and **Object Lock** protect important data; **event notifications** start processing such as scanning and resizing, which must be idempotent and free of loops.

## Key terms

- **S3** — Amazon Simple Storage Service, AWS's object storage.
- **Object storage** — Storing whole objects with keys and metadata, accessed over an API.
- **Bucket** — A named container for objects in one region.
- **Object** — Stored data plus its metadata.
- **Key** — An object's name within a bucket.
- **Prefix** — The beginning part of keys, used to group objects.
- **Block Public Access** — Settings that prevent buckets and objects from being made public.
- **Bucket policy** — A resource-based policy controlling access to a bucket.
- **SSE-S3 / SSE-KMS** — Server-side encryption with S3-managed or KMS-managed keys.
- **Pre-signed URL** — A signed, expiring URL that grants one operation on one object.
- **Pre-signed POST** — A signed browser form upload that can enforce conditions such as size.
- **Multipart upload** — Uploading an object in separately uploaded parts.
- **Storage class** — A price and access-speed tier for objects.
- **Lifecycle rule** — A rule that transitions or deletes objects automatically.
- **Versioning** — Keeping all versions of each object.
- **Delete marker** — A placeholder that hides an object in a versioned bucket instead of destroying it.
- **Object Lock** — Write-once protection that prevents deletion for a retention period.
- **Event notification** — A message S3 sends when objects change.
- **CORS** — Rules allowing browsers on other origins to call the bucket.
