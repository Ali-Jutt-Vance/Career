## Why this matters

So far, this part of the book has stored data in tables. **MongoDB** takes a different approach: it stores **documents** — JSON-like objects with nested fields and arrays — in **collections**. An order, with its items and delivery address, can be a single document that is read and written in one operation, without joins. Fields can differ from one document to the next, so a product catalogue where teas have caffeine levels and mugs have capacities fits naturally.

MongoDB is one of the most widely used databases in the world, popular in Node.js teams (its documents map directly to JavaScript objects), in content-heavy products, in catalogues, event logging and anywhere the data is naturally hierarchical. You will meet it in job descriptions, in existing systems, and in design discussions where someone asks, "should we use MongoDB or PostgreSQL?".

Answering that question well requires understanding what document databases are good at — and what they make harder. Flexibility without discipline produces inconsistent data; embedding without thought produces documents that grow without limit; and the absence of joins moves work into data modelling. This chapter covers MongoDB's model, its query and aggregation language, data modelling, indexes, validation and transactions, with every example run against a real MongoDB 8 server.

## The simple idea

A relational database is like a set of ledgers where each kind of fact has its own ledger and entries refer to each other by number. A document database is like a filing cabinet of folders: everything about one order — the customer reference, the items, the delivery address, the notes — goes into one folder. Pulling out the folder gives you the whole order at once. The folders in a drawer usually look similar, but nothing forces them to be identical.

> [!ANALOGY]
> A document database is like a filing cabinet where each folder holds everything about one thing — an order with its items and address — so one pull gives you the whole picture, whereas a relational database splits facts across separate ledgers linked by numbers.
>
> **Where the analogy breaks:** in a real office, nobody needs the same fact in many folders to stay identical. In a database, if a customer's name is copied into every order folder and then changes, all the copies must be updated — or deliberately left as historical snapshots. Deciding what goes in the folder and what stays a reference is the central design skill in MongoDB.

## The proper definition and key words

**MongoDB** is a document-oriented database that stores records as **BSON** documents (a binary form of JSON with extra types) in collections, with a rich query language, secondary indexes, an aggregation framework, replication and sharding.

Key words:

| Relational | MongoDB |
|---|---|
| Database | Database |
| Table | **Collection** |
| Row | **Document** |
| Column | **Field** |
| Primary key | **`_id`** (an `ObjectId` by default, or any unique value) |
| Join | **Embedding**, or **`$lookup`** in an aggregation |
| `GROUP BY` queries | **Aggregation pipeline** |

More terms:

- **BSON** — binary JSON with additional types: `ObjectId`, `Date`, 32- and 64-bit integers, `Decimal128`, binary data.
- **ObjectId** — a 12-byte identifier generated by the driver, roughly time-ordered.
- **Embedding** — storing related data inside a document (an order's items).
- **Referencing** — storing another document's `_id` (an order's `customerId`).
- **Update operator** — a command that changes part of a document: `$set`, `$inc`, `$push`, `$pull`, `$unset`.
- **Replica set** — a group of servers holding copies of the data, with one primary accepting writes ({{ch:replication}}).
- **Sharding** — splitting a collection across several servers by a shard key ({{ch:sharding}}).

## Working with documents

### Level 1 — Connecting and CRUD

The examples use the official Node.js driver (`npm install mongodb`) and a MongoDB server given by `MONGODB_URL` — for example, one started locally with Docker ({{ch:docker}}) or a free cloud cluster:

```ts
import { MongoClient } from "mongodb";

const client = await MongoClient.connect(process.env.MONGODB_URL ?? "mongodb://localhost:27017");
await client.db("cornershop").dropDatabase();          // start fresh so the example can be rerun
const db = client.db("cornershop");

type Product = { _id: string; name: string; category: string; price: number; stock: number; tags: string[] };
const products = db.collection<Product>("products");

await products.insertMany([
  { _id: "TEA-GRN", name: "Green Tea", category: "tea", price: 4.2, stock: 40, tags: ["organic", "vegan"] },
  { _id: "TEA-BLK", name: "Breakfast Tea", category: "tea", price: 3.8, stock: 0, tags: ["vegan"] },
  { _id: "COF-BNS", name: "Coffee Beans", category: "coffee", price: 9.5, stock: 12, tags: [] },
]);

// Find: a filter document, a projection and a sort
const teas = await products
  .find({ category: "tea", stock: { $gt: 0 } }, { projection: { _id: 0, name: 1, price: 1 } })
  .sort({ price: -1 })
  .toArray();
console.log("in-stock teas:", teas);

// Update operators change parts of a document in place
await products.updateOne({ _id: "TEA-BLK" }, { $inc: { stock: 25 }, $push: { tags: "fairtrade" } });
await products.updateOne({ _id: "COF-BNS" }, { $set: { price: 9.9, origin: { country: "Colombia", farm: "La Esperanza" } } });
console.log(await products.findOne({ _id: "TEA-BLK" }, { projection: { stock: 1, tags: 1 } }));
console.log(await products.findOne({ _id: "COF-BNS" }, { projection: { price: 1, origin: 1 } }));

// Documents in one collection need not have the same fields
console.log("with an origin:", await products.countDocuments({ origin: { $exists: true } }));

await client.close();
```

**Output:**

```text
in-stock teas: [ { name: 'Green Tea', price: 4.2 } ]
{ _id: 'TEA-BLK', stock: 25, tags: [ 'vegan', 'fairtrade' ] }
{
  _id: 'COF-BNS',
  price: 9.9,
  origin: { country: 'Colombia', farm: 'La Esperanza' }
}
with an origin: 1
```

- **Queries are documents.** `{ category: "tea", stock: { $gt: 0 } }` means "category equals tea and stock greater than 0". Operators include `$eq`, `$ne`, `$gt`, `$gte`, `$lt`, `$lte`, `$in`, `$nin`, `$exists`, `$regex`, `$and`, `$or`, and array operators such as `$all` and `$elemMatch`.
- **Projections** choose fields: `1` to include, `0` to exclude (`_id` is included unless excluded).
- **Update operators** modify documents in place, atomically: `$inc` adds to a number, `$push` appends to an array, `$set` sets fields — here adding a nested `origin` object that no other product has.
- **Flexible structure**: the coffee now has an `origin` field and the teas do not. Flexibility is useful; unchecked, it lets typos (`stok`) and inconsistent shapes creep in — which is why the validation shown later matters.
- **`_id`** is the primary key, always indexed and unique. Here the SKUs serve as `_id`s; by default the driver generates an `ObjectId`.
- In TypeScript, typing the collection (`collection<Product>`) gives typed filters and results. Many Node.js teams use **Mongoose**, an ODM (object–document mapper) that adds schemas, validation and middleware on top of the driver ({{ch:orms}}).

## Data modelling

### Level 2 — Embed or reference?

The central decision in MongoDB is what to put **inside** a document and what to keep in **separate** documents linked by id. The guiding principle: **data that is accessed together should be stored together.**

**Embed** when:

- the related data belongs to the parent and is read with it (an order's items, a product's dimensions);
- it is bounded in size (an order has tens of items, not millions);
- it is a snapshot that should not change with the source (the delivery address used for an order, {{ch:database-design}}).

**Reference** when:

- the related entity is shared and changes independently (customers, products);
- the list could grow without limit (a product's reviews, a user's activity events);
- the related data is often accessed on its own.

A single MongoDB document has a **16 MB** size limit — but long before that, unbounded arrays make documents slow to read and update. Useful patterns:

- **Subset pattern**: embed the latest few reviews in the product for the product page; keep all reviews in a separate collection.
- **Extended reference**: copy a few stable fields of a referenced document (the customer's name for display) alongside its id — accepting that the copy may need updating.
- **Bucket pattern**: group time-series data into documents per hour or day instead of one document per event. (MongoDB also has dedicated time-series collections.)

### Level 3 — An embedded order and the aggregation pipeline

Here an order embeds its items and a snapshot of the delivery address, and references its customer by id. One read returns the whole order; an **aggregation pipeline** computes revenue per customer and looks up their names:

```ts
import { MongoClient } from "mongodb";

const client = await MongoClient.connect(process.env.MONGODB_URL ?? "mongodb://localhost:27017");
await client.db("cornershop").dropDatabase();          // start fresh so the example can be rerun
const db = client.db("cornershop");

type Customer = { _id: string; name: string; city: string };
type Item = { sku: string; name: string; qty: number; unitPrice: number };
type Order = { _id: number; customerId: string; status: string; placedAt: Date; deliveryAddress: { line1: string; city: string }; items: Item[] };

// An order embeds its items and a snapshot of the delivery address; it references the customer by id
await db.collection<Customer>("customers").insertMany([
  { _id: "c1", name: "Sara Khan", city: "Leeds" },
  { _id: "c2", name: "Omar Ali", city: "Manchester" },
]);
const orders = db.collection<Order>("orders");
await orders.insertMany([
  { _id: 1042, customerId: "c1", status: "delivered", placedAt: new Date("2026-09-02T10:00:00Z"),
    deliveryAddress: { line1: "12 High St", city: "Leeds" },
    items: [{ sku: "TEA-GRN", name: "Green Tea", qty: 2, unitPrice: 4.2 }, { sku: "SNK-OAT", name: "Oat Biscuits", qty: 1, unitPrice: 2.5 }] },
  { _id: 1043, customerId: "c2", status: "delivered", placedAt: new Date("2026-09-20T12:00:00Z"),
    deliveryAddress: { line1: "4 Canal St", city: "Manchester" },
    items: [{ sku: "TEA-BLK", name: "Breakfast Tea", qty: 3, unitPrice: 3.8 }] },
  { _id: 1044, customerId: "c1", status: "cancelled", placedAt: new Date("2026-10-14T18:20:00Z"),
    deliveryAddress: { line1: "12 High St", city: "Leeds" },
    items: [{ sku: "COF-BNS", name: "Coffee Beans", qty: 1, unitPrice: 9.5 }] },
]);

// One read returns the whole order, items included: no joins
console.log(await orders.findOne({ _id: 1042 }, { projection: { _id: 0, status: 1, "items.name": 1, "items.qty": 1 } }));

// Aggregation pipeline: revenue per customer, with the customer's name looked up
const revenue = await orders.aggregate([
  { $match: { status: { $ne: "cancelled" } } },
  { $unwind: "$items" },
  { $group: { _id: "$customerId", revenue: { $sum: { $multiply: ["$items.qty", "$items.unitPrice"] } }, units: { $sum: "$items.qty" } } },
  { $lookup: { from: "customers", localField: "_id", foreignField: "_id", as: "customer" } },
  { $project: { _id: 0, customer: { $first: "$customer.name" }, revenue: { $round: ["$revenue", 2] }, units: 1 } },
  { $sort: { revenue: -1 } },
]).toArray();
console.log(revenue);

await client.close();
```

**Output:**

```text
{
  status: 'delivered',
  items: [ { name: 'Green Tea', qty: 2 }, { name: 'Oat Biscuits', qty: 1 } ]
}
[
  { units: 3, customer: 'Omar Ali', revenue: 11.4 },
  { units: 3, customer: 'Sara Khan', revenue: 10.9 }
]
```

The pipeline is a list of **stages**, each transforming the stream of documents from the previous one — like a Unix pipe, or the steps of a SQL query written out in order:

1. **`$match`** filters documents (like `WHERE`) — cancelled order 1044 is dropped. Put `$match` early so indexes can be used and later stages handle fewer documents.
2. **`$unwind`** turns each order into one document per item.
3. **`$group`** groups by customer and sums `qty × unitPrice` (like `GROUP BY` with `SUM`).
4. **`$lookup`** fetches matching customer documents into an array (a left outer join).
5. **`$project`** reshapes the output: the first looked-up name, revenue rounded to 2 places.
6. **`$sort`** orders the results.

Other common stages: `$limit`, `$skip`, `$count`, `$addFields`/`$set`, `$facet` (several pipelines at once), `$bucket`, and `$merge`/`$out` (write results to a collection, like a materialised view, {{ch:normalization}}).

**About money:** the example stores prices as JavaScript numbers (BSON doubles) for readability, and rounds the result. Real financial data should use **`Decimal128`** (or integer pennies), exactly as `numeric` is used in PostgreSQL ({{ch:sql}}).

## Indexes

### Level 3 — The same principles as SQL

MongoDB indexes are B-trees, and almost everything from {{ch:indexes}} applies: index the fields you filter and sort on, order compound index fields by equality, then sort, then range, and check plans with `explain()`:

```ts
import { MongoClient } from "mongodb";

const client = await MongoClient.connect(process.env.MONGODB_URL ?? "mongodb://localhost:27017");
await client.db("cornershop").dropDatabase();          // start fresh so the example can be rerun
const events = client.db("cornershop").collection("events");

await events.insertMany(Array.from({ length: 20000 }, (_, i) => ({
  customerId: `c${i % 500}`, type: i % 10 === 0 ? "purchase" : "page_view", at: new Date(Date.UTC(2026, 0, 1) + i * 60_000),
})));

const query = { customerId: "c40", type: "purchase" };
const before = await events.find(query).explain("executionStats");
console.log("no index:  ", before.queryPlanner.winningPlan.stage, "examined", before.executionStats.totalDocsExamined, "returned", before.executionStats.nReturned);

await events.createIndex({ customerId: 1, type: 1, at: -1 });
const after = await events.find(query).sort({ at: -1 }).explain("executionStats");
const stage = (p: any): string => (p.inputStage ? `${p.stage} → ${stage(p.inputStage)}` : p.stage);
console.log("with index:", stage(after.queryPlanner.winningPlan), "examined", after.executionStats.totalDocsExamined, "returned", after.executionStats.nReturned);

await client.close();
```

**Output:**

```text
no index:   COLLSCAN examined 20000 returned 40
with index: FETCH → IXSCAN examined 40 returned 40
```

- Without an index, MongoDB performs a **`COLLSCAN`** (collection scan) — reading all 20,000 documents to return 40, like a sequential scan.
- With a compound index on `{ customerId: 1, type: 1, at: -1 }` — two equality fields, then the sort field — the plan becomes **`IXSCAN`** (index scan) followed by **`FETCH`** of exactly the 40 matching documents, already in the requested order (no in-memory sort stage).
- Other index types: **unique** indexes, **partial** indexes (`partialFilterExpression`), **TTL** indexes that delete documents automatically after a time (sessions, temporary data), **multikey** indexes on array fields (created automatically when a field holds arrays), **text** indexes, and **2dsphere** indexes for geographic queries.
- Every index slows writes and uses memory; the same discipline applies as in PostgreSQL. Build indexes on large production collections carefully and watch their effect.

## Keeping data correct

### Level 3 — Validation, atomic updates and transactions

Flexibility does not mean anything goes. MongoDB can **validate** documents with JSON Schema; **single-document operations are atomic**, so conditional updates prevent overselling; and **multi-document transactions** make several changes all-or-nothing when they span documents:

```ts
import { MongoClient, MongoServerError } from "mongodb";

const client = await MongoClient.connect(process.env.MONGODB_URL ?? "mongodb://localhost:27017");   // transactions need a replica set
await client.db("cornershop").dropDatabase();
const db = client.db("cornershop");

// Schema validation: the database rejects documents that break the rules
await db.createCollection("products", {
  validator: { $jsonSchema: {
    bsonType: "object",
    required: ["name", "price", "stock"],
    properties: {
      name: { bsonType: "string", minLength: 1 },
      price: { bsonType: ["double", "int", "decimal"], minimum: 0 },
      stock: { bsonType: "int", minimum: 0 },
    },
  } },
});
const products = db.collection<{ _id: string; name: string; price: number; stock: number }>("products");
await products.insertMany([{ _id: "TEA-GRN", name: "Green Tea", price: 4.2, stock: 5 }, { _id: "COF-BNS", name: "Coffee Beans", price: 9.5, stock: 1 }]);
try {
  await products.insertOne({ _id: "BAD", name: "Broken", price: -1, stock: 3 });
} catch (err) {
  console.log("rejected:", (err as MongoServerError).code, (err as MongoServerError).errmsg);
}

// Atomic conditional update: only succeeds if enough stock remains
const reserve = (sku: string, qty: number) =>
  products.findOneAndUpdate({ _id: sku, stock: { $gte: qty } }, { $inc: { stock: -qty } }, { returnDocument: "after" });
console.log("reserve 1 coffee:", (await reserve("COF-BNS", 1))?.stock);
console.log("reserve 1 more:  ", await reserve("COF-BNS", 1));

// A multi-document transaction: an order and stock changes commit together or not at all
const orders = db.collection<{ _id: number; items: { sku: string; qty: number }[] }>("orders");
const session = client.startSession();
try {
  await session.withTransaction(async () => {
    await orders.insertOne({ _id: 1, items: [{ sku: "TEA-GRN", qty: 2 }, { sku: "COF-BNS", qty: 1 }] }, { session });
    for (const [sku, qty] of [["TEA-GRN", 2], ["COF-BNS", 1]] as const) {
      const r = await products.updateOne({ _id: sku, stock: { $gte: qty } }, { $inc: { stock: -qty } }, { session });
      if (r.modifiedCount === 0) throw new Error(`${sku}: not enough stock`);
    }
  });
} catch (err) {
  console.log("transaction aborted:", (err as Error).message);
} finally {
  await session.endSession();
}
console.log("orders:", await orders.countDocuments(), "green tea stock:", (await products.findOne({ _id: "TEA-GRN" }))?.stock);

await client.close();
```

**Output:**

```text
rejected: 121 Document failed validation
reserve 1 coffee: 0
reserve 1 more:   null
transaction aborted: COF-BNS: not enough stock
orders: 0 green tea stock: 5
```

- **Validation**: the negative price was refused with error code **121**. Validators enforce required fields, types and ranges; set `validationAction: "error"` (the default) so violations are rejected rather than merely logged. Application-side validation still gives friendlier messages ({{ch:validation}}).
- **Atomic conditional update**: `findOneAndUpdate` with `stock: { $gte: qty }` in the filter and `$inc` in the update is one atomic operation — the same pattern as `UPDATE … WHERE stock >= qty` ({{ch:transactions}}). The first reservation took the last bag of coffee; the second found no matching document and returned `null`. No race can oversell.
- **Transaction**: inside `session.withTransaction`, the order insert and green-tea reservation succeeded, but coffee was sold out, so the callback threw — and **everything rolled back**: no order exists and green tea is still 5. Every operation must pass `{ session }`; one without it runs outside the transaction. `withTransaction` also retries automatically on transient errors.
- **Transactions need a replica set** (or a sharded cluster), which is the normal production setup; the example's server is a single-node replica set.

Because one document can hold an order **with** its items, many operations that need transactions in a relational database are a single atomic write in MongoDB. Good modelling reduces the need for multi-document transactions; when they are needed, keep them short ({{ch:transactions}}).

### Level 4 — Consistency settings

MongoDB lets each operation choose how strong its guarantees are:

- **Write concern** — how many replica-set members must acknowledge a write. `w: "majority"` (the default) means the write survives the loss of the primary; `w: 1` is faster and can lose recent writes on failover.
- **Read concern** — what data a read may see: `"local"` (fastest, may later be rolled back), `"majority"` (only data acknowledged by a majority).
- **Read preference** — whether reads go to the primary or may use secondaries (which can return slightly stale data, {{ch:replication}}).

The defaults are sensible for most applications; weakening them is a deliberate trade of durability or freshness for speed.

## MongoDB or PostgreSQL?

### Level 4 — Choosing

| MongoDB fits well when | PostgreSQL fits well when |
|---|---|
| Data is naturally hierarchical and read as whole documents (catalogues, content, profiles, orders with items) | Data is highly relational, with many entities joined in many ways |
| Shapes vary a lot between records or change frequently | Strong constraints across entities matter (foreign keys, unique rules, exclusion constraints) |
| Very large scale-out with built-in sharding is a real requirement | Complex ad-hoc queries, reporting and analytics on operational data are common |
| The team models around access patterns and keeps documents bounded | Many writes span several entities and need transactions routinely |

The gap has narrowed: PostgreSQL's JSONB stores and indexes documents ({{ch:postgresql}}), and MongoDB has transactions, schema validation and joins through `$lookup`. Many teams use PostgreSQL by default and add MongoDB (or JSONB) where documents clearly fit. The decision should come from the data's shape, the access patterns and the team's experience — not from fashion. Whatever you choose, plan **indexes**, **validation** and **backups** from the start.

## From beginner to enterprise

**Level 1–2 — first MongoDB app.** Collections and documents; `insertOne`/`insertMany`, `find` with filters and projections, `updateOne` with operators, `deleteOne`; typed collections or Mongoose models.

**Level 3 — sound application design.** Embedding versus referencing based on access patterns; bounded arrays; snapshots versus references; aggregation pipelines with early `$match`; compound indexes checked with `explain()`; JSON Schema validation; atomic conditional updates.

**Level 4 — production.** Replica sets with majority write concern; multi-document transactions where needed; TTL and partial indexes; monitoring slow queries (the profiler, Atlas performance tools); backups and restores tested; `Decimal128` for money.

**Level 5 — senior practice.** Sharding with a well-chosen shard key ({{ch:sharding}}); schema versioning and migrations for changing document shapes; change streams feeding other systems ({{ch:event-driven-systems}}); capacity planning.

**Level 6 — enterprises.** Multi-region clusters, data residency, queryable encryption for sensitive fields, governance of schemas across many teams, and polyglot persistence with clear ownership of each data store.

## Real-world use cases

### A product catalogue with varied attributes

- **Design**: one `products` collection; common fields (`sku`, `name`, `price`, `category`, `stock`) validated by JSON Schema; category-specific attributes in an `attributes` sub-document; compound indexes on `{ category: 1, price: 1 }`; text index for search; the latest five reviews embedded (subset pattern) and all reviews in a separate collection.

### An activity feed

- **Design**: events in a time-series collection (or bucketed documents per user per day), indexed by `{ userId: 1, at: -1 }`; a TTL index removes events older than 90 days; an aggregation pipeline produces daily summaries written with `$merge` to a summary collection.

## Common mistakes

### Beginner: treating MongoDB as schemaless

**Consequence:** inconsistent field names and types across documents. **Fix:** JSON Schema validation, typed collections or Mongoose schemas.

### Beginner: copying a relational schema one-to-one

Every entity in its own collection, joined with `$lookup` everywhere. **Fix:** model around access patterns; embed what is read together.

### Beginner: unbounded embedded arrays

**Consequence:** huge, slow documents approaching the 16 MB limit. **Fix:** reference growing data; subset and bucket patterns.

### Intermediate: missing indexes

**Fix:** index filter and sort fields; check `explain("executionStats")` for `COLLSCAN`.

### Intermediate: read–modify–write in application code

**Consequence:** lost updates. **Fix:** update operators with conditions in the filter (`$inc`, `findOneAndUpdate`).

### Intermediate: doubles for money

**Fix:** `Decimal128` or integer minor units.

### Production: forgetting `{ session }` in transactions

**Fix:** pass the session to every operation inside the transaction.

### Production: weakening write concern for speed without understanding it

**Consequence:** acknowledged writes lost on failover. **Fix:** majority write concern for important data.

## Debugging and troubleshooting

- **Query is slow**: `explain("executionStats")` — `COLLSCAN`, high `totalDocsExamined` versus `nReturned`, or an in-memory `SORT` stage indicate a missing or misordered index.
- **"Transaction numbers are only allowed on a replica set member or mongos"**: transactions need a replica set — even locally, run a single-node replica set.
- **Document failed validation (code 121)**: inspect `errInfo` on the error for the rule that failed.
- **Duplicate key error (code 11000)**: a unique index rejected the write — handle as a conflict.
- **Documents growing large or updates slowing down**: unbounded arrays — check document sizes (`$bsonSize` in an aggregation) and restructure.
- **Aggregation exceeds memory**: large `$group` or `$sort` stages — `$match` earlier, add indexes for the initial stages, or allow disk use (`allowDiskUse: true`).

## Security summary

- **Enable authentication and TLS**; never expose MongoDB to the internet without them — open databases have been mass-scanned and held for ransom.
- Use **least-privilege users** per application (`readWrite` on one database, not `root`).
- Beware **NoSQL injection**: if a request body is passed straight into a filter, an attacker can send `{ "password": { "$ne": null } }` instead of a string. Validate input types ({{ch:validation}}) and never build filters directly from untrusted objects.
- Do not evaluate user-supplied JavaScript (`$where`, `$function`) in queries.
- Encrypt sensitive fields (client-side field-level or queryable encryption) where required; protect and test **backups**.

## How a senior engineer thinks about this

- **Model for access patterns.** What is read together is stored together; what grows without limit is referenced.
- **Flexibility needs discipline.** Validation, typed code and schema versioning keep documents consistent.
- **Atomicity lives at the document level.** Good document design turns many transactions into single atomic writes.
- **Indexes and plans matter as much as in SQL.** They check `explain()` for every important query.
- **Choose by fit, not fashion.** They can explain why MongoDB or PostgreSQL (or both) suits a particular system.

## Exercises

### Exercise 1 — Model a blog

**Objective:** practise embedding versus referencing.
**What to do:** design collections for a shop's blog: posts (title, body, author, tags, publication date), authors (name, bio, avatar), and comments (author name, text, date — some posts get thousands). The post page shows the post, the author's name and avatar, and the latest 10 comments; an author page lists their posts.

<details>
<summary>Show the solution</summary>

- **`authors`**: `{ _id, name, bio, avatarUrl }` — shared and changing independently, so referenced.
- **`posts`**: `{ _id, slug, title, body, tags: [...], publishedAt, author: { _id, name, avatarUrl }, commentCount, latestComments: [ ...up to 10 ] }` — an **extended reference** copies the author's name and avatar for the post page (update them in posts when an author changes them — rare), and the **subset pattern** embeds the newest 10 comments.
- **`comments`**: `{ _id, postId, authorName, text, createdAt }` — all comments, because they grow without limit; indexed by `{ postId: 1, createdAt: -1 }` for "load more".
- **Indexes**: `posts` on `{ slug: 1 }` (unique), `{ "author._id": 1, publishedAt: -1 }` for author pages, `{ tags: 1, publishedAt: -1 }` for tag pages.
- **Writing a comment**: insert into `comments`, then `$push` with `$slice: -10` into `latestComments` and `$inc` `commentCount` (in a transaction if exact consistency matters, or accept brief inconsistency).

</details>

### Exercise 2 — Write the pipeline

**Objective:** practise aggregation.
**What to do:** using the `orders` documents from this chapter, write a pipeline that returns, for each product SKU sold in non-cancelled orders, the total quantity and the number of orders it appeared in, most units first.

<details>
<summary>Show the solution</summary>

```ts
// fragment
const bySku = await orders.aggregate([
  { $match: { status: { $ne: "cancelled" } } },
  { $unwind: "$items" },
  { $group: { _id: "$items.sku", units: { $sum: "$items.qty" }, orders: { $addToSet: "$_id" } } },
  { $project: { _id: 0, sku: "$_id", units: 1, orderCount: { $size: "$orders" } } },
  { $sort: { units: -1, sku: 1 } },
]).toArray();
```

`$unwind` produces one document per item; `$group` sums quantities and collects distinct order ids with `$addToSet`; `$size` counts them. For the chapter's data this returns Breakfast Tea (3 units, 1 order), Green Tea (2, 1) and Oat Biscuits (1, 1). An index on `status` (or a compound index starting with it) supports the initial `$match` on larger collections.

</details>

### Exercise 3 — Find the injection

**Objective:** practise spotting NoSQL injection.
**The scenario:** a login route does `const user = await users.findOne({ email: req.body.email, password: req.body.password })`. Explain the attack and fix it (two problems).

<details>
<summary>Show the solution</summary>

**Attack:** the body is JSON, so an attacker can send `{ "email": "admin@cornershop.example", "password": { "$ne": null } }`. The filter then means "email equals admin and password is not null", which matches — logging in as admin without a password. This is **NoSQL injection**.

**Fixes:**
1. **Validate types**: accept only strings for `email` and `password` (for example, with a Zod schema, {{ch:validation}}); reject objects. Some drivers and ODMs offer filter sanitising, but explicit validation is the real fix.
2. **Never store or compare plaintext passwords**: find the user by email only, then verify the password against a stored hash with a slow password-hashing function ({{ch:authentication}}).

</details>

### Exercise 4 — Production scenario: the slowing user documents

**Objective:** practise diagnosing modelling problems.
**The scenario:** a `users` collection embeds each user's `activity` array, to which every page view is pushed. After a year, profile loads take seconds for active users, updates are slow, and some writes fail with "document too large". What happened and how do you fix it?

<details>
<summary>Show the solution</summary>

**What happened:** an **unbounded array**. Active users' documents grew to many megabytes; every profile read loads the whole array; every `$push` rewrites a large document; the heaviest users hit the 16 MB limit.

**Fix:**
1. Move activity to its own collection — `activity { userId, type, at, … }` — ideally a time-series collection or bucketed per user per day, indexed by `{ userId: 1, at: -1 }`, with a TTL index if old events can expire.
2. Keep only small summaries on the user document (`lastActiveAt`, counters, perhaps the latest five events using `$push` with `$slice`).
3. Migrate in batches: copy each user's array into the new collection, then `$unset` the field; deploy code that writes to the new collection first, reads from both during the migration, then reads only the new one (expand–contract, {{ch:database-design}}).
4. Add monitoring of document sizes and a code-review rule: no unbounded arrays in documents.

</details>

## Summary

**MongoDB** stores **documents** — BSON objects with nested fields and arrays — in **collections**, each with a unique **`_id`**. Queries are documents with operators (`$gt`, `$in`, `$exists`…); **projections** select fields; **update operators** (`$set`, `$inc`, `$push`…) change parts of documents atomically. Structure is flexible, so discipline comes from **JSON Schema validation**, typed code or Mongoose.

Modelling decides what to **embed** (data read together, bounded, owned or snapshotted — such as an order's items and delivery address) and what to **reference** (shared, independently changing or unbounded data — such as customers and reviews), with patterns such as subset, extended reference and bucketing, and the 16 MB document limit in mind. The **aggregation pipeline** processes documents through stages — `$match`, `$unwind`, `$group`, `$lookup`, `$project`, `$sort` — for reports and joins.

**Indexes** work much like PostgreSQL's B-trees: compound indexes ordered by equality, sort and range turn a `COLLSCAN` into an `IXSCAN`, verified with `explain("executionStats")`; TTL, partial, unique, multikey, text and geospatial indexes serve special needs. Single-document operations are atomic, so conditional updates prevent races; **multi-document transactions** (on replica sets, passing the session to every operation) cover changes spanning documents; write and read concerns tune durability and freshness. Choose MongoDB where documents fit the data and access patterns, PostgreSQL where relationships and cross-entity constraints dominate — and secure either with authentication, TLS, least privilege and protection against NoSQL injection.

## Key terms

- **MongoDB** — A document database storing BSON documents in collections.
- **Document database** — A database that stores records as self-contained documents rather than rows.
- **Document** — A single MongoDB record, a set of field–value pairs that can nest.
- **Collection** — A group of documents, comparable to a table.
- **BSON** — The binary JSON format MongoDB uses, with extra types such as dates and decimals.
- **_id** — The unique primary key field of every MongoDB document.
- **ObjectId** — MongoDB's default 12-byte, roughly time-ordered identifier.
- **Projection** — The specification of which fields a query returns.
- **Update operator** — An operator such as `$set`, `$inc` or `$push` that modifies part of a document.
- **Embedding** — Storing related data inside a document.
- **Referencing** — Storing the identifier of a document in another collection.
- **Extended reference** — Copying a few fields of a referenced document alongside its id.
- **Subset pattern** — Embedding a small, frequently used part of a larger related dataset.
- **Bucket pattern** — Grouping many small records, such as events, into documents per time period.
- **Aggregation pipeline** — A sequence of stages that transform and summarise documents.
- **$lookup** — The aggregation stage that joins documents from another collection.
- **$unwind** — The aggregation stage that outputs one document per array element.
- **COLLSCAN / IXSCAN** — Query plan stages for scanning a whole collection or an index.
- **explain()** — A method that shows how MongoDB plans and executes a query.
- **TTL index** — An index that automatically deletes documents after a period.
- **Multikey index** — An index on an array field, with an entry per element.
- **Schema validation** — Rules, often in JSON Schema, that the database enforces on documents.
- **Decimal128** — BSON's exact decimal type, suitable for money.
- **Multi-document transaction** — An all-or-nothing group of operations across several documents.
- **Replica set** — A group of MongoDB servers holding copies of the same data with one primary.
- **Write concern** — The level of acknowledgement required before a write is considered successful.
- **Read concern** — The consistency level of the data a read may return.
- **Mongoose** — A popular object–document mapper for MongoDB in Node.js.
- **NoSQL injection** — An attack that injects query operators through untrusted input.
